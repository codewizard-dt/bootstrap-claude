Follow-on research answering: can installing `relates_to::[[obsidian]]` itself and the three typed-link plugins (`relates_to::[[dataview]]`, `relates_to::[[graph-link-types]]`, `relates_to::[[breadcrumbs-plugin]]`) be automated into this repo's setup/update scripts, opt-in but recommended, and which skills would actually benefit? `derived_from::[[obsidian-wiki-linking]]` — this report takes that prior research's "currently zero plugins installed, zero authoring changes needed" finding as given and asks whether the remaining manual step (installing the app + plugins) can be removed. **Both halves are fully automatable with no invented pattern required.** Installing the Obsidian app is a single native-package-manager command per OS — `brew install --cask obsidian` (macOS), `winget install -e --id Obsidian.Obsidian` (Windows; the winget manifest itself declares `InstallModes: [silent]`), `flatpak install flathub md.obsidian.Obsidian` (Linux — the officially verified, auto-updating path, preferred over `.deb`/AppImage/Snap because those don't self-update).

Installing the three plugins needs **no running Obsidian process and no GUI at all**. Obsidian's own plugin loader is just files on disk: a `manifest.json` + `main.js` (+ optional `styles.css`) dropped into `<vault>/.obsidian/plugins/<id>/`, where `<id>` must exactly match the `id` field inside that plugin's own `manifest.json` (not the GitHub repo name — a robust installer fetches `manifest.json` first to read the authoritative id before naming the directory), plus listing that id in `<vault>/.obsidian/community-plugins.json`. This is directly scriptable via each plugin's GitHub Releases API (`GET api.github.com/repos/<owner>/<repo>/releases/latest`). **BRAT is irrelevant to this design** — it's a GUI-side convenience plugin that itself needs manual bootstrapping inside a running Obsidian instance before it can fetch anything, not a headless scripting primitive.

This repo already has a reusable "guarded, opt-in, sticky-preference" install pattern — `register_optional_mcp`/`_add_playwright`/`_add_brave` in `lib/scripts/install-mcps.sh`, and the `OPTIONAL_GUIDES` loop in `lib/scripts/sync-wiki-scaffold.sh` — that a new `lib/scripts/install-obsidian.sh` should reuse rather than reinvent, wired into `run_project_sync()` (`lib/scripts/lib.sh`) right after the wiki-scaffold sync step and before the MCP-guide build. Recommended preference keys: `obsidian.installApp` (global scope, sticky, mirrors `mcp.playwright`'s machine-wide scope) and `obsidian.plugins` (project scope, sticky, bundles all three plugins behind one prompt since Dataview is a hard prerequisite for the other two — unlike MCPs, which are pitched and toggled independently). Both must default to a real opt-in prompt, never a silently-defaulted `true`, since **community plugins execute arbitrary JS with full vault read/write access and no granular permission system** — a genuine supply-chain trust decision. `.obsidian/` is already gitignored, so everything this automation writes stays machine-local, consistent with the existing MCP-registration model.

Which skills benefit is **not uniform**, and this is the load-bearing judgment call of the report. `/wiki-lint` and `raw/llm-wiki.md`'s existing graph-view guidance improve for free — relation labels on `rel::[[target]]` edges simply appear once Graph Link Types is installed, with zero skill-file changes, because that guidance already recommends the graph view as a human cross-check. **`/task-audit` does NOT automatically benefit** — its dependency block (`lib/skills/task-audit/SKILL.md` Step 2e) parses a bespoke `> **Depends on**: [...]` blockquote of plain markdown links, not the `rel::[[target]]` inline-field convention these plugins read. Reconciling the two formats (or configuring a Breadcrumbs custom-regex source against the existing blockquote) is a deliberate, separately-scoped follow-on task, not a side effect of installing plugins. `wiki-dashboard-server.js` should not be replaced or deprioritized by any of this — it serves `wiki/work/` over plain HTTP with zero local-app dependency, complementary to (not competing with) Obsidian-based exploration for CI, remote agents, or teammates without Obsidian installed.
