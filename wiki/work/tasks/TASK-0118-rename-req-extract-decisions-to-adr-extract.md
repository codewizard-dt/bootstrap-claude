# TASK-0118 — Rename req-extract-decisions to adr-extract and re-home it as an ADR-side skill that takes a PRD or any document as its source

relates_to::[[wiki-skill-boilerplate-duplication]]
depends_on::[[TASK-0117]]
blocks::[[TASK-0119]]

## Objective

Hard-rename `lib/skills/req-extract-decisions` to `lib/skills/adr-extract` and change what it is: it stops being a PRD-side skill that only operates inside the requirements family and becomes an **ADR-side** skill that takes a *source document* — a PRD (by ID, `NNNN-slug`, bare number, or path) **or any other document path** — and produces ADR candidates (Decision Group candidates for `/adr-create`) from it. The **Architecturally Significant Requirement (ASR) extraction algorithm is preserved unchanged** (the section-scan map, the boundary rule, the existing-decision tag-overlap cross-check, the grouping and per-group confirmation). What changes is the skill's name, description, `argument-hint`, source resolution, which family it reads and writes, and every reference to it across the repo. A residue-sweep test asserts no live `req-extract-decisions` reference remains outside historical records. Roadmap item: ROADMAP-0014 Phase 4 ("Rename `req-extract-decisions` → `adr-extract`"); binding decisions are Q&A item 1 (rename to `adr-extract`, ADR-side, takes a PRD or other document), items 2-4 (new-item IDs are `PRD-`/`ADR-`; existing `REQ-`/`DEC-` IDs resolve via `aliases:` until the migration task; directories keep their names; hard rename, no redirect stub) and the Phase 4 sequencing note in that roadmap's Notes.

## Approach

**Sequencing**: runs after TASK-0117 (the ADR family rename, which itself follows the PRD family rename in the chain), so by the time this task starts, `decision-create`/`decision-finalize`/`decision-walkthrough`/`decision-next` are `adr-*`, the requirements-family skills are `prd-*` (except `req-retire`, renamed later to `prd-deprecate`), `ID-RESOLUTION.md`'s family table carries the `PRD`/`ADR` prefixes, and new items are created `PRD-NNNN`/`ADR-NNNN`. Precedes TASK-0119. Because neighbouring tasks edit the same files (`ID-RESOLUTION.md`, `README.md`, `CLAUDE.md`, `lib/skills/README.md`, both renamed-family `SKILL.md`s, the two contract tests), every edit is a minimal exact-string edit made after a **fresh re-read** — never a whole-file rewrite. Wherever this task's text names another skill (`/prd-finalize`, `/adr-create`, `/task-create`), use the name that exists on disk at execution time, not the name in this file.

**Source-of-truth note**: edit `lib/skills/`, never `~/.claude/skills/`. Do **not** touch the installed `~/.claude/skills/req-extract-decisions/` copy and do **not** run `install-global.sh` — TASK-0122 (the installer prune) removes stale installed skills. Note `lib/scripts/install-global.sh` already contains the legacy name `prd-extract-decisions` in its `ORPHAN_SKILLS` array (from an earlier rename); that is the one legitimate home of old skill names — leave it untouched.

**New source semantics (design decided here, autonomously)**:

| Aspect | Before (`req-extract-decisions`) | After (`adr-extract`) |
|--------|----------------------------------|-----------------------|
| Position | PRD-side; `family: requirements` only | ADR-side; source can be a PRD **or any document** |
| Argument | `<path/to/req.md, NNN-slug, or NNN>` | `<PRD ID / NNNN-slug / NNNN / path, or path to any document>` |
| Source resolution | ID-RESOLUTION, requirements, refuses non-`approved` | **PRD mode**: input is not a path, or is a path under `wiki/work/requirements/` → resolve via `ID-RESOLUTION.md` (`family: requirements · scope: active · ambiguous: interactive`), gate on `status: approved`. **Document mode**: input is a path (contains `/` or ends `.md`) that is **not** under `wiki/work/requirements/` → confirm it exists with `find_file` (missing: STOP `File not found: <path>`, never create), skip the ID-RESOLUTION wiring line and the status gate. The `ID-RESOLUTION.md` procedure itself is **not modified** (it correctly rejects out-of-family paths; the skill decides the mode before invoking it) |
| Empty input | pick-list of `approved` requirements | same pick-list (PRD mode), via `AskUserQuestion` |
| ASR scan map (Step 3) | keyed on PRD section names | unchanged for a PRD; for a document, scan every heading section with the same ASR taxonomy and the same verbatim-traceability rule, using the document's own section titles in the "Source Section" column |
| Writes in PRD mode | PRD's `## Linked Decisions` table + `updated`; `Source REQ:` back-link on reused decisions; log line | same two-sided linkage; back-link becomes `Source PRD: [PRD-NNNN](../requirements/PRD-NNNN-slug.md)`; the idempotency check treats an existing `Source PRD:` **or legacy `Source REQ:`** line for the same item (matched by ID or alias) as already present |
| Writes in document mode | n/a | **read-only except the log entry** — no PRD to hold a `## Linked Decisions` table and no decision back-links; the completion report prints the ASR/coverage/grouping tables and the `/adr-create` commands, each suffixed `(from <document path>)` |
| Log line | `## [date] req-extract-decisions \| REQ-NNNN <title> — N ASRs identified` | `## [date] adr-extract \| <PRD-NNNN or document path> <title> — N ASRs identified` |
| Emitted next commands | `/decision-create group: <slug> (from REQ-NNNN)`, `/task-create --req REQ-NNNN "…"` | `/adr-create group: <slug> (from PRD-NNNN or <path>)`, `/task-create --req PRD-NNNN "…"` (PRD mode only; in document mode, non-architectural ASRs are listed without a `--req` form) |
| Metadata | `category: planning`, `model: claude-opus-5`, `effort: high` | unchanged |

**Section-name rule**: the PRD's ASR-bearing sections and its `## Linked Decisions` table heading are owned by the PRD template (`lib/skills/prd-create/SKILL.md`, renamed by TASK-0116). Re-read that skill's section list at execution time and mirror whatever heading it actually uses; do not rename the heading in this task.
