# TASK-0122 — Make install-global.sh prune stale skill directories from ~/.claude/skills/ via a maintained stale-skills.json

relates_to::[[skill-family-rename-pattern]]
depends_on::[[TASK-0121]]
depends_on::[[TASK-0107]]
blocks::[[TASK-0123]]

## Objective

`install-global.sh` rsyncs `lib/skills/` into `~/.claude/skills/` but never deletes anything, so every hard-renamed or removed skill (ROADMAP-0014 Phase 4: `task-audit`, `task-trash`, `task-add`, `uat-generate`, `bug-file`, `req-update`, `task-update`, `req-create`, `req-finalize`, `req-compile`, `req-retire`, `req-extract-decisions`, `decision-create`, `decision-finalize`, `decision-walkthrough`, `decision-next`, plus earlier removals such as `roadmap-add`) lingers on every already-installed machine as a duplicate slash command next to its replacement. Make the installer prune exactly those directories, driven by a checked-in, one-entry-per-retired-skill data file, so the Phase 4 no-redirect-stub policy (Q&A decision 4, ROADMAP-0014 Notes, 2026-09-19) actually holds for existing installs. Roadmap item: ROADMAP-0014 Phase 4 ("Make `install-global.sh` prune stale skill directories …").

## Approach

**Sequencing (binding, ROADMAP-0014 Notes).** Runs after TASK-0121 so the final rename/removal list is settled, and after TASK-0107 (already landed, `pending-uat`) which added step 7b (`configure_sandbox`, `install-global.sh` ~lines 330–424) to the same file. This task's edit lives entirely in **step 2** (the skills install, lines ~38–80) and the file header (lines ~10–14), far from 7b, so 7b, its `SANDBOX_CONFIGURED` summary token and `SUMMARY_TOKENS` are not touched. Re-read `install-global.sh` immediately before editing; other tasks edit it. Precedes TASK-0123.

**Finding that shapes the design — an existing mechanism already does a smaller version of this, and its list becomes dangerous after Phase 4.** `install-global.sh` already has an `ORPHAN_SKILLS` array (`adr-create adr-finalize adr-next adr-walkthrough prd-create prd-finalize prd-extract-decisions prd-update prd-trash prd-compile`, lines 10–14) and a `skills.pruneOrphans` sticky prompt (lines 47–80; schema key at `bootstrap-prefs-schema.json:147`). Phase 4 renames `decision-*` → `adr-*` and `req-*` → `prd-*`, so **`adr-create`, `adr-finalize`, `adr-next`, `adr-walkthrough`, `prd-create`, `prd-finalize` and `prd-compile` become live skill names again**. Step 2 rsyncs *before* it prunes, so the old array would delete the freshly installed live skills. This task therefore replaces `ORPHAN_SKILLS` and the sticky prompt wholesale rather than adding a second mechanism beside them, and adds a structural guard (a name that exists in the source `lib/skills/` is never pruned) so this class of collision cannot recur when a name is later reused.

**Design.**

| Piece | Decision |
|-------|----------|
| List | `lib/scripts/templates/stale-skills.json` — single source of truth, checked in, pure data (no comments, `JSON.parse`-able), same "template owns the canonical data" model as `settings-deny.json`. Shape: `{ "skills": [ { "name": "task-audit", "replacedBy": "task-assess", "retiredIn": "TASK-0110" }, … ] }`. `replacedBy` is `null` for skills removed with no replacement (`req-update`, `task-update`, `roadmap-add`). `retiredIn` records the task/roadmap that retired it — the "release/task it was retired in" audit trail |
| Logic | New zero-dependency Node script `lib/scripts/prune-stale-skills.js`, sibling of `merge-settings-deny.js`/`merge-settings-hooks.js` (same house style: always exits 0, warn-and-continue, `--target`-style seams for tests). Not bash: frontmatter parsing, symlink checks and JSON validation are unsafe to hand-roll in shell around `rm -rf` |
| What it deletes | Only `<skills-dir>/<name>` for `name` exactly in the data file, and only when **all** hold: `name` matches `^[a-z0-9][a-z0-9-]*$` (no path traversal); the path is a real directory, **not a symlink**; it contains a `SKILL.md` whose frontmatter `name:` equals the entry's `name` (quotes tolerated); and `name` is **not** a directory in the source `lib/skills/` (the live-name guard). A same-named user skill with a different `name:`, a directory with no `SKILL.md`, or a symlinked skill is left in place with a one-line note saying why |
| Reach | Never touches anything under `~/.claude` except those exact skill directories: not `hooks/`, `templates/`, `settings.json`, prefs, or other skills |
| Output | One line per removal, e.g. `  - removed stale skill: task-audit (replaced by task-assess; retired in TASK-0110)`, one line per deliberate skip, and a one-line total; **silent when there is nothing to do** so a second run is a clean no-op |
| Idempotence | Removal makes the entry inapplicable next run; no state is stored |
| Failure | Exit 0 always; unreadable/malformed data file, missing skills dir, or a per-directory `rmSync` failure prints a `Warning:` to stderr and continues; `install-global.sh` additionally wraps the call in `if ! node … ; then echo "Warning: …" >&2; fi` so `set -euo pipefail` never aborts the local installs (same pattern as step 7b and step 8) |
| Test seam | `--skills-dir <dir>` (default `$HOME/.claude/skills`), `--source-skills-dir <dir>` (the live-name guard's reference), `--data <file>`, and `--dry-run` (prints `would remove …` lines, deletes nothing, safe to run against a real HOME). `install-global.sh` passes only `--source-skills-dir "$TEMPLATE_DIR/lib/skills"`; it gains no `--dry-run` of its own (its other steps have no dry-run mode and a partial one would mislead) |

**Unconditional, not preference-gated (decision made here so `/tackle` need not re-decide).** Every listed old name no longer exists in the repo, so the entry can only ever match a stale installed copy or a user's coincidentally same-named custom skill — and the `name:`-equality + symlink + live-name guards already protect the latter. There is nothing left for a user to opt into: declining just leaves a dead duplicate slash command, and the Phase 4 policy is explicitly no redirect stubs. Unconditional-with-printout also removes the failure mode the sticky prompt has today: a non-interactive run (CI, `setup`/`update` piped) answers "no" and never cleans up, and a remembered decline hides the stale folders forever. The trade-off accepted: a user whose own custom skill happens to carry *exactly* a retired name in its `name:` field loses it — mitigated by the printed removal line, the exact-name rule, and the fact that such a skill would already collide with the historical repo skill. Consequently the `skills.pruneOrphans` preference is **retired** in this task (schema entry, README registry row, tests); a stored `skills.pruneOrphans` value in a user's `bootstrap-prefs.json` becomes an ignored unknown key (verify in Step 4 that reads and `--list` tolerate it, per `bootstrap-prefs.js`'s "unknown key on read" contract).

**Seed list = the lead's list, reconciled against `lib/skills/` at implementation time.** Initial entries: `task-audit`→`task-assess`, `task-trash`→`task-close`, `task-add`→`task-create`, `uat-generate`→`uat-create`, `bug-file`→`bug-create`, `req-update`, `task-update`, `req-create`→`prd-create`, `req-finalize`→`prd-finalize`, `req-compile`→`prd-compile`, `req-retire`→`prd-deprecate`, `req-extract-decisions`→`adr-extract`, `decision-create`→`adr-create`, `decision-finalize`→`adr-finalize`, `decision-walkthrough`→`adr-walkthrough`, `decision-next`→`adr-next`, plus earlier removals: `roadmap-add` (removed in a5dafe3, ROADMAP-009) and the surviving legacy names from the old array that are **not** live after Phase 4 — `prd-extract-decisions`, `prd-update`, `prd-trash`. Note `req-retire` is on the roadmap item's list though the lead's message omitted it; include it. The exact `replacedBy`/`retiredIn` values for the TASK-0116..0121 renames are filled from those task files once they exist. Drop any name that is a directory in the final `lib/skills/`.

**Retained on purpose.** `wiki/knowledge/sources/req-to-requirement-rename.md` mentions `ORPHAN_SKILLS`; it is a summary of an immutable raw source (historical), so it is not edited. The concept page `skill-family-rename-pattern.md` describes the *current* mechanism and is revised in place (Step 6).
