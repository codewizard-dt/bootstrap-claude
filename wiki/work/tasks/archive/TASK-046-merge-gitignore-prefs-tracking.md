# TASK-046 — merge-gitignore.sh — prefs.gitTracking three-way prompt and declines-only wiring

part_of::[[ROADMAP-005]]

## Objective

Add the new `prefs.gitTracking` three-way prompt to `lib/scripts/merge-gitignore.sh` — deciding how git treats `.claude/bootstrap-prefs.json` and its generated `.claude/bootstrap-prefs.README.md` — and wire the script's three existing prompts (the master review gate, the per-section offer, the `.git/info/exclude` consent) to the preference store as **declines only**, so a remembered "no" stops the re-offer while a remembered "yes" can never silently append lines to a project's `.gitignore` on a later run. The invariant at `merge-gitignore.sh:11` — *"NOTHING is ever added to a project's .gitignore without asking"* — must survive this task verbatim.

## Approach

**The declines-only rule is enforced in the schema data, and call sites must not re-implement it.** `gitignore.section.*` has a one-value grammar of `false` (`bootstrap-prefs-schema.json`), so `bootstrap-prefs.js --set <section-key> --value true` **exits 1** — a caller bug, loudly. That is the design: an accepted section is never recorded, so a section that gains new lines in a later template version is still offered by title on the next run rather than appended silently. Never write a `true` for a section key, and never add a call-site guard that duplicates the grammar check — a second copy of the rule is a second place for it to be wrong.

**Shell out to `bootstrap-prefs.js --section-key <title>` for every section key. Do not slugify in `awk`/`sed`.** One `templates/gitignore` banner title contains an **em dash (U+2014)**: `Claude Code — machine-local MCP registration (absolute paths; regenerated by setup)`. A byte-wise `[^a-z0-9]` slugifier — the obvious shell implementation — sees that one character as three UTF-8 bytes and emits three dashes, producing a key that does not match the one the schema documents. The stored decline then silently stops matching and the prompt re-asks forever, which is the precise failure this roadmap exists to remove. `--section-key` is Unicode-aware (JS regex with the `u` flag) and exists so the slug rule has exactly one implementation. `test/bootstrap-prefs.test.js` already pins both the em-dash title's presence in the template and its expected key.

**The master gate is a `scope: either` key and must be read with `--project "$PROJECT_DIR"`.** `gitignore.offerSectionUpdates` is the one Phase 2 key whose resolution walks project → global → schema default, so it is read directly with `prefs_get` rather than through `prompt_yn_sticky` (whose single-selector design is documented as correct for `global`/`project` keys only). Its three-way behavior, straight from the schema:

| Resolved value | Behavior |
|---|---|
| `false` | skip the whole section pass, no prompt at all |
| `true` | run the section pass **without** the opening question — each section is still offered by title, so nothing is appended silently |
| `ask` | today's behavior: the opening `Review .gitignore updates? (N line(s) across M section(s))` prompt |

**Its schema `default` is `true`, not `ask`, and that is intentional.** An unanswered key therefore drops the opening gate and goes straight to the per-section offers. It looks like a behavior change and it is one — but the invariant holds, because every individual section is still offered by title before a single line is written. Implement what the schema says; do not "fix" the default. Record a decline of the opening gate as `false` (that is the declines-only wiring for this prompt) and record nothing on an accept.

**`prefs.gitTracking` is the one key here that is recorded in all three directions.** It is a choice among three outcomes, not a yes/no on adding lines, so the declines-only rule explicitly does not apply — the schema says so. Values `gitignore | exclude | neither`, default `exclude`, and it covers **both** files together: `.claude/bootstrap-prefs.json` and `.claude/bootstrap-prefs.README.md`. They must stay in the same directory precisely so one answer can govern both.

```
  How should .claude/bootstrap-prefs.json be treated by git?
    [1] .gitignore          — ignored for everyone who clones this repo (shared decision)
    [2] .git/info/exclude   — ignored on this machine only, teammates unaffected (default)
    [3] neither             — commit it, so the whole team shares these answers
```

Chicken-and-egg is fine and needs no special handling: the values file is created by the first recorded answer, the question is asked after, and `[3] neither` is the no-op that leaves prior state untouched. Option `[1]` writes to `.gitignore` while the user is being asked, explicitly, right then — so the invariant holds there too.

**Ask `prefs.gitTracking` LAST, after both existing passes.** By then any answer recorded earlier in the run has already created `<project>/.claude/bootstrap-prefs.json` and its companion, so the paths being ignored actually exist and the user can see what they are agreeing about.

**The `.git/info/exclude` layout is load-bearing and easy to break.** `exclude_is_canonical` (`:209`) requires the sentinel line followed **immediately** by `.serena/`, `raw/`, `wiki/` in that order, terminated by a `#` comment or EOF, and `~/.claude/file-suggestion.sh` parses exactly that block to restore `@`-autocomplete. `exclude_normalize` (`:246`) scrubs the sentinel and those three exact paths from anywhere in the file and re-appends the canonical block **at the bottom**, keeping every other line verbatim. So the two prefs paths must:

- go under their **own** `#` comment header (e.g. `# bootstrap preferences (machine-local)`), never bare;
- never be placed between the sentinel and `wiki/`, which would make them "stranded" entries that `exclude_stranded` reports and the next normalize pushes above the block anyway;
- survive a later `exclude_normalize` unchanged, which they do because the scrub only removes the sentinel and the three known paths.

Write them **before** calling `exclude_apply` (or anywhere above the sentinel block), then let normalize re-append its block at the bottom. Verify `exclude_is_canonical` still returns true afterwards — if it does not, the next run silently rewrites the file every time.

**`gitignore.infoExclude` is declines-only too, and the pure-repair path stays prompt-free.** A decline records `false` and suppresses the re-offer; an accept records nothing, because accepting changes the world and `exclude_is_canonical` already makes it sticky. The `elif`/`else` structure at `:309-325` must keep its shape: a file where all three paths are already excluded elsewhere is a **pure repair** and runs with no prompt regardless of the stored value. Do not let a stored `false` block that repair — the schema is explicit that a pure sentinel repair runs with no prompt at all regardless of this key.

**The script is already interactive-only** (`:40` exits when `--interactive` is absent or there is no tty), so the "only record an answer that was actually asked interactively" rule is satisfied structurally here. It still must not be circumvented: every recorded answer goes through TASK-043's helpers, which make the non-interactive `--set` unreachable.

**Keep the three git-adjacent keys distinct in the code as well as in the prose.** `gitignore.infoExclude` (`.serena/`, `raw/`, `wiki/`), `gitignore.offerSectionUpdates` (whether the section pass runs), and `prefs.gitTracking` (the two prefs files) are three different questions; the schema cross-references them in all three directions and a test pins those cross-references. Declining one must not disable another — most damagingly, declining the section pass must leave the `.git/info/exclude` mechanism fully working.
