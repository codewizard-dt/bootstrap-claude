# UAT Walkthrough

Interactively walk through each test in a pending UAT file, presenting instructions to the user and recording pass/fail results.

---

**UAT File**: $ARGUMENTS

---

## Pipeline Context

This command is part of the task lifecycle: `/add-task` → `/tackle` → `/uat-generator` → **`/uat-walkthrough`**

UAT files are generated by `/uat-generator` and placed in `.docs/uat/pending/`.

---

## Cycle Overview

This command runs in a continuous loop, presenting one test at a time to the user:

```
┌──────────────────────────────────────────────────────────────────┐
│  1. READ UAT FILE → 2. FIND NEXT TEST → 3. PRESENT TO USER      │
│         ↑                                        │               │
│         │                                        ↓               │
│         └──────── 5. UPDATE FILE ← 4. RECORD VERDICT ───────────┘
└──────────────────────────────────────────────────────────────────┘
```

---

## Step 1: Read and Parse the UAT File

- Read the UAT file at: `$ARGUMENTS`
- If the file does not exist or is empty, STOP and report the error
- If the file is not in `.docs/uat/pending/`, warn the user and confirm they want to proceed
- Parse the structure to identify:
  - **Test sections**: Headings matching `### UAT-*` patterns (e.g., `### UAT-API-001:`, `### UAT-UI-002:`)
  - **Prerequisites**: Items under `## Prerequisites`
  - **Test status**: Each test ends with `- [ ] Pass` (pending) or `- [x] Pass` (passed) or `- [FAIL] ...` (failed)
- Count totals: passed, failed, pending, skipped

---

## Step 2: Find the Next Pending Test

### Priority Order
1. **Prerequisites first**: If any prerequisite is unchecked (`- [ ]`), present it before tests
2. **Failed tests**: If any test is marked `[FAIL]`, ask the user if they want to re-test it
3. **Next pending test**: Find the first test with `- [ ] Pass`

### Completion Check
- If ALL tests are marked `[x] Pass` or `[FAIL]`:
  - Report the final summary
  - If all passed, move the file from `pending/` to `complete/`
  - STOP

---

## Step 3: Present the Test to the User

For the current test, present a clear, formatted briefing:

### Presentation Format

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
TEST [X of Y]: UAT-API-001 — List All Positions
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Endpoint: GET /api/v1/positions
Description: Verify positions list endpoint returns user's positions

STEPS:
  1. Execute: curl -X GET 'http://localhost:8000/api/v1/positions' \
       -H 'Authorization: Bearer <token>'

EXPECTED RESULT:
  200 OK with array of position objects containing
  id, symbol, size, entry_price, current_price, pnl

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Progress: 2/8 passed · 0 failed · 6 remaining
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**Rules for presenting**:
- Extract ALL metadata fields from the test (Endpoint, Page, Scenario, Components, Description, Steps, Expected Result)
- Number the test position (e.g., "Test 3 of 12")
- Show current progress bar/counts
- If steps include curl commands or code, format them clearly for copy-paste

---

## Step 4: Record the User's Verdict

Use `AskUserQuestion` to get the result:

### Question Format

Ask the user: **"What is the result of this test?"**

Options:
1. **Pass** — Test passed as expected
2. **Fail** — Test did not produce expected results
3. **Skip** — Skip this test for now (will remain pending)
4. **Abort** — Stop the walkthrough entirely

### If Pass
- Mark the test: `- [x] Pass <!-- YYYY-MM-DD -->`

### If Fail
- Ask a follow-up: **"Describe what went wrong (optional):"** — use `AskUserQuestion` with a freeform "Add notes" option
- Mark the test: `- [FAIL: <user's note or "No details provided">] <!-- YYYY-MM-DD -->`

### If Skip
- Leave the test unchanged (`- [ ] Pass`)
- Move to the next test

### If Abort
- Save current progress (all updates already written)
- Report summary and STOP

---

## Step 5: Update the UAT File

After each verdict:

1. **Update the test's status line** in the file using Edit tools:
   - Replace `- [ ] Pass` with the appropriate marker (see Step 4)
2. **Do NOT modify** any other part of the test — only the status line changes

### Example Updates

**Pass**:
```markdown
Before: - [ ] Pass
After:  - [x] Pass <!-- 2026-03-03 -->
```

**Fail**:
```markdown
Before: - [ ] Pass
After:  - [FAIL: Returns 401 instead of 200, token may be expired] <!-- 2026-03-03 -->
```

---

## Step 6: Repeat the Cycle

After updating:

1. **Return to Step 1** — Re-read the file to get current state
2. **Find next pending test** — Step 2
3. **Present** — Step 3
4. **Record** — Step 4
5. **Update** — Step 5
6. **Continue** until all tests are resolved or user aborts

---

When the walkthrough ends (all tests resolved or user aborts), report:

### Summary Format

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
UAT WALKTHROUGH COMPLETE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
File:    .docs/uat/pending/5-positions.uat.md
Source:  .docs/tasks/active/5-positions.md

Results:
  ✓ Passed:  6
  ✗ Failed:  2
  - Skipped: 0
  Total:     8

Failed Tests:
  • UAT-API-003: Delete Position — "Returns 500 instead of 204"
  • UAT-EDGE-001: Empty Positions — "Loading spinner never resolves"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### Post-Walkthrough Actions

- **All passed**: Move file from `.docs/uat/pending/` to `.docs/uat/complete/` and report the new path
- **Some failed**: Keep file in `pending/`. Suggest next steps:
  ```
  To fix failures and re-test:  /uat-walkthrough .docs/uat/pending/<file>.uat.md
  To create fix tasks:          /add-task "Fix UAT failures in <feature>"
  ```
- **Aborted**: Keep file in `pending/`, note progress was saved

## Important Rules

### User Interaction
- **Never skip the user prompt** — every test requires explicit pass/fail from the user
- **Never auto-pass or auto-fail** — the user is the tester, the agent is the facilitator
- Present one test at a time — do not batch multiple tests into one question
- Keep the test presentation clean and scannable

### File Integrity
- Only modify status lines (`- [ ] Pass` → `- [x] Pass` or `- [FAIL: ...]`)
- Never rewrite or reformat the rest of the UAT file
- Preserve all existing metadata, headings, and structure

### Prerequisites
- Walk through prerequisites first, one at a time
- For each prerequisite, ask the user to confirm it's ready
- If a prerequisite fails, warn the user that subsequent tests may be affected but let them decide whether to continue

### Progress Persistence
- Every verdict is written to the file immediately — if the user aborts or the session ends, progress is preserved
- On resuming a partially-completed walkthrough, it picks up from the first pending test
