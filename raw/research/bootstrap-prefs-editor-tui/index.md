# Research: A non-Claude-Code editor for bootstrap-prefs.json

> Build a standalone, zero-dependency Node CLI (`bootstrap-prefs-tui.js`, wired as a new `bootstrap config` subcommand) that ports the existing `/bootstrap-config` Socratic flow — read state, explain the key, offer only legal values, confirm, write — onto Node's built-in `readline` module. It reuses `bootstrap-prefs.js` unchanged as the read/write engine, so validation, atomic writes, and scope enforcement are inherited for free. Do **not** make the read-only `dashboard` HTTP server writable — that flips a documented design invariant, adds an unauthenticated local write surface (CSRF-from-any-open-browser-tab risk even when bound to `127.0.0.1`), and buys little since `bootstrap-prefs.json` is a flat, ~20-key file that a menu-driven terminal flow already serves well. A small **read-only** "Settings" panel on the dashboard is a reasonable complementary addition later, but should link out to the CLI/TUI to actually change anything.

## Research Questions

1. What does "user/project settings" refer to in this codebase, and what shape does that data have?
2. What does the existing Claude-mediated editor (`/bootstrap-config`) already do, and how much of it is reusable without Claude?
3. Is a standalone interactive TUI (readline-based, zero deps) or a web UI piggybacked on the `dashboard` command the better fit, given this repo's stated zero-dependency policy?
4. What do current (2025–2026) Node.js practices say about building CLI prompts without a dependency, and what do lightweight prompt libraries cost if a dependency were allowed?
5. What security considerations apply if a local HTTP server is made writable, and how does that compare to a CLI?

## Current State (Codebase)

- **Scope decision**: per user confirmation, this research covers only `bootstrap-prefs.json` — the flat key/value preference store this repo already built — not Claude Code's own `~/.claude/settings.json` / `.claude/settings.local.json` (permissions/hooks/env), which is a separate, more complex nested structure maintained by `lib/scripts/merge-settings-deny.js` and `lib/scripts/merge-settings-hooks.js`.
- **The engine already exists and is solid**: `lib/scripts/bootstrap-prefs.js` (`/Users/davidtaylor/Repositories/bootstrap-claude/lib/scripts/bootstrap-prefs.js`) is a dependency-free Node script implementing `--get` / `--set` / `--unset` / `--list` / `--section-key` against two flat JSON layers (global `~/.claude/bootstrap-prefs.json`, project `<repo>/.claude/bootstrap-prefs.json`). It already does everything a UI would need: schema-driven validation (`allowedValues`), scope enforcement (`scopePermitsLayer`, refuses a write into a layer the key's `scope` forbids — BUG-0009 fix), atomic writes (`writeAtomic`, temp-file + rename), indentation preservation, and companion-doc regeneration (`bootstrap-prefs.README.md`). Any new editor should call this script (or its logic) rather than re-implement writes.
- **The schema is small and flat**: `lib/scripts/templates/bootstrap-prefs-schema.json` defines ~20 concrete keys plus two `dynamic: true` families (`guides.*`, `gitignore.section.*`). Each entry has `scope` (`global`/`project`/`either`), `consumer` (`installer`/`skill`), `summary`, a long `detail` paragraph, a `values` grammar (pipe-delimited enum, e.g. `true | false | ask`), an optional `default`, and `askedBy`. This is exactly the shape a menu-driven form handles well — no free-text values, no nesting, no arrays.
- **`/bootstrap-config`** (`lib/skills/bootstrap-config/SKILL.md`) is the current front end — a Claude Code slash command that runs the helper via `Bash`, reads the schema via `Read`, and drives the user through a 7-step flow (locate → read state → print summary → pick mode → pick key → pick value+layer → confirm+write → re-verify) using `AskUserQuestion`. This is a well-specified *algorithm*, not something intrinsically tied to an LLM: every step is a deterministic read of the schema plus a menu choice. It is the natural spec to port into a standalone script.
- **The `dashboard` command** (`lib/scripts/wiki-dashboard-server.js`, dispatched by `bin/cli.js`'s `SCRIPTS.dashboard`) is a zero-dependency Node `http` static file server, explicitly documented (own header comment, and Serena memory `components/wiki-dashboard`) as serving the wiki tree **read-only**: `GET /` → `dashboard.html` SPA, `GET /wiki/**` → path-traversal-guarded file reads. There is no POST handling, no write path, and no auth of any kind today — it relies entirely on "nobody but you can reach your loopback interface" for its threat model.
- **A real, verifiable gap in that threat model today**: `wiki-dashboard-server.js`'s `listen(port, callback)` call passes no host argument, so Node's default bind is **all interfaces** (`0.0.0.0`), not `127.0.0.1`. In practice this means the (read-only, today) dashboard is already reachable from other devices on the same LAN/Wi-Fi, not just localhost — worth fixing regardless of what the settings-editor decision is, and a materially bigger problem the moment any write capability is added to that server.
- **Zero-dependency policy is explicit and consistent**: `package.json` declares no `dependencies` or `devDependencies` at all; every script in `lib/scripts/` is either Bash or dependency-free Node; `wiki-dashboard-server.js`'s own comment reads "Node builtins only." Any solution that pulls in an npm package (even a small one) is a policy break, not a neutral technical choice, and should be flagged as such rather than silently introduced.
- **The CLI already has the right shape for a new subcommand**: `bin/cli.js` dispatches via a flat `SCRIPTS` map (`setup`, `update`, `install`, `migrate`, `typechecks`, `dashboard`), each entry naming a script and its args, run with `execFileSync(..., { stdio: 'inherit' })`. Adding e.g. `config: { script: 'bootstrap-prefs-tui.js', args: ['.', ...extraArgs] }` is a two-line, precedent-following change.

## Key Findings

- Node's built-in `readline` module is routinely used in 2025–2026 guidance as the correct zero-dependency choice for a "minimal interactive CLI" — one current guide states plainly, "For a minimal interactive CLI, I still use Node's built-in readline module," reserving external prompt libraries for cases needing masked input (passwords) or richer widgets [S1]. It supports the exact primitives a settings menu needs: numbered lists via `rl.question`, arrow-key/keypress handling via `readline.emitKeypressEvents`, and clean teardown via `rl.close()` — no dependency required [S1][S2].
- A 2026 comparison of interactive-prompt options states the current smallest/leanest widely-used library is `@clack/prompts` (~2KB) — called "the new standard for CLI prompts" for elegance and bundle size — with `enquirer` (~100KB) preferred when richer prompt types (autocomplete, date picker) are needed, and `ink` (~150KB + React) reserved for CLIs with complex live-updating state (progress bars, nested rendering) [S3]. None of these is zero-dependency; all would be a first-ever runtime dependency for this package.
- Library-comparison data (npm trends) shows `inquirer` (43.2M weekly downloads, 21.5k stars) and `prompts` (43.8M weekly downloads, 9.3k stars) are both larger and more actively used than `enquirer` (27.2M downloads, 7.9k stars); guidance elsewhere singles out `prompts` specifically as "if bundle size is a critical concern and you want a lightweight, unopinionated library" [S4][S5]. This matters only if the zero-dependency policy is ever revisited — for the current, flat, ~20-key schema, plain `readline` is sufficient and keeps the policy intact.
- Security guidance on local HTTP servers is unambiguous and repeated across multiple 2025 sources: **never bind to `0.0.0.0`** for a tool meant to be local-only — "some people will wrongly suggest exposing on `0.0.0.0` which is not loopback, and WILL expose your server to the local network. So don't do that... `127.0.0.1` or the `localhost` keyword is what you want" [S6][S7].
- Binding to loopback is necessary but **not sufficient** for a write-capable local server: from a browser's perspective "`localhost` (or `127.0.0.1`) is just another domain name," so any web page open in the same browser can still issue cross-origin requests to it — "the attacker doesn't need to access your server directly. They access it through your browser" [S8]. A JSON `POST` (not a "simple" content type) does trigger a CORS preflight that a server without deliberate CORS/Origin handling will typically not satisfy, but this is a property you must design for explicitly, not one that "localhost-only" gives you automatically — the linked write-up frames this as the "critical misunderstanding" developers have about local dev servers [S8]. `localhost` and `127.0.0.1` are also *not* treated as the same origin by browsers for cookie/CSRF purposes, which is a common source of surprising same-origin-check bugs if that technique is used [S9].

## Constraints

- Must not introduce a new runtime dependency if the zero-dependency policy is to be preserved (`package.json` has none today).
- Must reuse `bootstrap-prefs.js` as the single read/write engine — it already owns validation, scope enforcement, atomic writes, and companion-doc regeneration; re-implementing any of that in a second place would create two sources of truth for a store the codebase is deliberately careful about (see BUG-0009 in the schema's own commentary).
- Must work from a plain terminal invocation with **no Claude Code session running** — the entire point of the request.
- Should follow the `bin/cli.js` `SCRIPTS` map convention so it is reachable as `npx @codewizard-dt/bootstrap <command>`, consistent with `dashboard`, `setup`, etc.
- Should not weaken the dashboard's existing "read-only" design invariant (documented in its own header comment and in Serena memory `components/wiki-dashboard`) without a deliberate, separately-flagged decision — that invariant is presently what makes its complete lack of auth defensible.
- The `guides.*` and `gitignore.section.*` dynamic families need a "list concrete keys found in the consulted files, or show the pattern with an explanation if none exist" behavior, exactly as `--list` and `/bootstrap-config` Step D/E already implement — a port must not silently drop this.

## Recommendation

**Build Option A**: a standalone, zero-dependency `bootstrap-prefs-tui.js`, wired into `bin/cli.js` as a new `config` (or `prefs`) subcommand, so the workflow becomes `npx @codewizard-dt/bootstrap config` from any terminal with no Claude Code session.

Implementation outline:

1. **Port the algorithm, not just the intent.** `lib/skills/bootstrap-config/SKILL.md` Steps A–G are already a complete, deterministic spec (locate helper+schema → run `--list` → group by `consumer` → mode menu → key menu with `Other` free text → value+layer menu parsed from the schema's `values` string → confirmation → run `--set`/`--unset` → re-`--list` and print the diff). Translate each step directly into a `readline`-driven menu loop; do not redesign the flow.
2. **Never re-implement validation, scope rules, or writes.** Shell out to `bootstrap-prefs.js` (`execFileSync`) for every `--get`/`--set`/`--unset`/`--list` exactly as the skill does via `Bash` today — this is what keeps BUG-0009's scope-enforcement fix, atomic writes, and companion-doc regeneration correct without a second implementation to drift out of sync.
3. **Reuse the schema JSON directly** for `detail`, `values`, `scope`, `consumer`, and the two `dynamic: true` families, same as the skill's Step B/D/E — a JS `require`/`readFileSync` + `JSON.parse`, no new format.
4. **Wire it into `bin/cli.js`**: add `config: { script: 'bootstrap-prefs-tui.js', args: ['.', ...extraArgs] }` to the `SCRIPTS` map and a usage line, matching the existing `dashboard` entry's pattern (`args: ['.', ...extraArgs]`).
5. **Support both interactive and flag-driven use** per general Node CLI best practice — "Don't force user interactivity if a command-line argument can be auto-detected... Aim to provide a works-out-of-the-box experience" [S2] — so `bootstrap config` with no args opens the menu, while `bootstrap config --get <key>` / `--set <key> <value> --project|--global` can shell straight through to the helper for scripting.
6. **Leave the dashboard read-only for now.** Its current design is sound for its stated purpose; do not fold settings-editing into it in this pass.

Risks and mitigations:

- *Risk*: two editors (skill + TUI) drift in behavior over time. *Mitigation*: both read the same schema file and both delegate to the same `bootstrap-prefs.js`; only the presentation loop is duplicated, and it is a direct port, so future schema changes (new keys, new `dynamic` families) are picked up by both automatically without either needing an update.
- *Risk*: `readline`'s raw-mode/keypress handling is fiddlier to get right than a library's (terminal resize, Ctrl-C during a prompt, non-TTY/piped stdin). *Mitigation*: current guidance stresses treating `readline` "like a phone call" — always close the interface, gate interactivity behind a TTY check, and handle SIGINT explicitly [S1][S2]; a simple numbered-menu-and-`rl.question()` design (no full-screen redraw, no raw keypress capture) sidesteps almost all of this and is the same interaction style `npm init`-era tools have used for years.
- *Risk*: scope creep into "let's also make it fancy" pulls in a dependency anyway. *Mitigation*: name the zero-dependency constraint explicitly in the task/PR description so it's a deliberate checkpoint, not an assumption; if the team later decides bundle size is genuinely not a concern for this package, `@clack/prompts` (~2KB) is the leanest current option [S3] and `prompts` (~43.8M weekly downloads) the most bundle-size-conscious of the widely-adopted ones [S4][S5] — but that is a distinct decision from "should this exist," and should be its own `/decision-create` if raised.

Alternative if constraints change: if the team decides the *visual, clickable* editing experience matters enough to justify the security work, Option B becomes viable — but only after (a) fixing `wiki-dashboard-server.js`'s bind address to `127.0.0.1` explicitly regardless, and (b) designing real CSRF defenses (e.g., requiring a custom request header only same-origin `fetch()` can set, checking `Origin`/`Referer` on state-changing routes, and never accepting a settings change via `GET`) rather than relying on "it's just localhost."
