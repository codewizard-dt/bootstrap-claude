# Research: Gating `package-install-consent.js` via a Sentinel/Preference Instead of Always Blocking

> `package-install-consent.js` is a `PreToolUse` hook that unconditionally denies every package-manager install command (`npm install`, `pip install`, `uvx --from`, etc.) with one hardcoded exception (Serena's own repo). This is **documented as deliberate friction, not a bug** — but the codebase already has a mature, four-state preference-store convention (`bootstrap-prefs.js`) that no hook currently uses. The recommended fix is a new **project-scoped** `true | false | ask` preference, consumed directly by the hook, defaulting to `false` (today's behavior unchanged) — with `ask` emitting the officially-documented `permissionDecision: "defer"` (handing back to Claude Code's own native permission prompt) and `true` emitting `"allow"` outright. The main real design decision isn't the mechanism — it's `askedBy`: this would be the **first bootstrap-prefs key ever consumed by a `lib/hooks/*.js` file**, and the schema's `consumer` enum (`installer | skill`) and its `askedBy`-must-resolve-to-`lib/scripts/`-or-a-slash-command test have no path for a hook today.

## Research Questions
- How does `package-install-consent.js` currently decide to block, and why was it built as an unconditional hook rather than a `permissions.ask` rule?
- How does this repo's existing preference-store convention (`bootstrap-prefs.js`) work, and does anything in `lib/hooks/` already consume it?
- What does the official Claude Code hook contract actually allow a `PreToolUse` hook to return, beyond bare deny?
- What would a sentinel-file design look like compared to reusing the existing preference store, and which fits this codebase better?
- What concrete schema/test/doc changes would implementing this require?

## Current State (Codebase)

**The hook itself** (`lib/hooks/package-install-consent.js`) is a zero-dependency Node script, matcher `Bash`, sharing `lib/hooks/lib/command-parse.js` for stdin parsing and a `deny()` helper [S1]. Its logic: strip `VAR=… env sudo` prefixes, tokenize each `;`/`&&`/`||`/`|`-separated segment, match the manager's basename against a table of install subcommands (`npm install|i|add`, `pnpm add|install`, `yarn add`, `pip(3) install`, `uv pip install`, `pipx install`, `gem install`, `cargo install`, `go install`, `brew install`), and separately match `uvx --from <source>` unless `<source>` is Serena's own repo URL (`SERENA_SOURCE` regex) [S1]. `--dry-run`/`--help`/`-h` are recognized as non-installing. Every match calls `deny()`, which prints `{hookSpecificOutput: {hookEventName: 'PreToolUse', permissionDecision: 'deny', permissionDecisionReason: ...}}` and exits 0 [S2] — **unconditional**, with no preference check anywhere in the file today.

The file's own header comments already justify the design in detail [S1]:
- *Why a hook, not a deny rule*: a deny rule can't carry the Serena exception — deny beats allow at every scope, and a hook returning `allow` can't loosen an existing deny rule, but a hook can simply choose not to deny.
- *Why not `permissions.ask`*: this repo runs headless (`claude -p` under `/uat-auto-plus` and power-mode) where nobody is present to answer a prompt, and a hanging/blocking ask is worse than a hard deny with copy-pasteable instructions.
- *Fails: open* — a thrown exception anywhere in the file exits 0 with no output (via `command-parse.js`), so a hook bug never bricks the user's shell.
- *Not gated by construction*: installs **inside** shell scripts (e.g. `bash lib/scripts/install-mcps.sh`) never reach this hook at all, since `PreToolUse` only sees the top-level command Claude asked to run — consent for the script as a whole already happened.
- `lib/hooks/README.md` states plainly: *"Known friction, real and expected... It is the one genuine friction point this gate introduces in-repo — not a bug. Approve it by running it yourself."* [S3] This is the exact friction the user is now asking to make configurable — the maintainers knew about it and chose it deliberately, which means any fix should preserve an equally-deliberate default, not silently soften the guarantee.

**The preference store** (`lib/scripts/bootstrap-prefs.js`) is a separate, mature, already-battle-tested convention: a flat dotted-key → value JSON store at two layers (`~/.claude/bootstrap-prefs.json` global, `<project>/.claude/bootstrap-prefs.json` project), resolved `project → global → schema default → unset`, validated against `lib/scripts/templates/bootstrap-prefs-schema.json` [S4]. Every key has `scope` (`global|project|either`), `consumer` (`installer|skill` — **only two values, hardcoded as `LEGAL_CONSUMERS` in `test/bootstrap-prefs.test.js:2075`** [S5]), and `askedBy`, which `test/bootstrap-prefs.test.js:2599` enforces must be **either** a `/slash-command` resolving to a real `lib/skills/<name>/SKILL.md`, **or** a bare filename (no `/`) resolving to a real file under `lib/scripts/` [S6]. `bootstrap-prefs.js` itself has **no `module.exports`** and no `require.main` guard — it is a pure CLI script, always invoked as `node bootstrap-prefs.js --get/--set/... `, never `require()`d [S7]. Every existing consumer (bash installers via `lib.sh`'s `prefs_get`/`prefs_set` wrappers, and slash-command skills via `node ~/.claude/bootstrap-prefs.js --get <key> --project .`) goes through this same CLI invocation — there is no in-process reuse path today.

**Confirmed: zero `lib/hooks/*.js` files reference `bootstrap-prefs` today** (`search_for_pattern` for `bootstrap-prefs` across `lib/hooks/` returned no matches). Every "escape hatch" documented for the existing command-class guards (`interpreter-indirection-guard.js`, `absolute-path-guard.js`, `mv-absolute-path-block.js`, `serena-*-guard.js`, etc.) is a **command-rephrasing trick** — retype it differently, write to a file first, join with `&&` instead of `|` — never a stored preference or sentinel file [S8]. Gating a hook via a persisted, structured preference would be a genuinely new integration pattern for this class of file, not an extension of an existing one.

## Key Findings

1. **The Claude Code hook contract supports four decision states, not just deny.** `permissionDecision` legally takes `"allow" | "deny" | "ask" | "defer"` [S9, S10, S11] — `S11` is this repo's own already-vetted wiki page (`wiki/knowledge/entities/components/bootstrap-claude-hooks.md`), which independently corroborates the `defer` value my own web search only surfaced via a lower-confidence secondary-source summary. `defer` is the officially-documented way to hand the decision back to Claude Code's normal permission-mode handling — the precise mechanism, not an informal "omit the field" workaround. `package-install-consent.js`'s shared `command-parse.js` only exports a `deny()` helper today [S2] — there is no `allow()`/`defer()` counterpart anywhere in this codebase's hooks. This means a preference-gated version of this hook has **three natural outcomes**: keep denying (today), explicitly `allow` (skip even Claude Code's native prompt), or explicitly `defer` (hand back to Claude Code's own permission-mode handling — interactive: the normal native "allow this?" UI prompt; `bypassPermissions`/headless: proceeds, the same trade-off every other already-permitted command already accepts under bypass).
2. **The existing `true | false | ask` grammar (used by `gitCommit.autoPush`, `research.persistToRaw`, etc.) maps onto this almost exactly**, with `ask` meaning something subtly different for a hook than for a skill: a skill's `ask` means "the skill prompts via `AskUserQuestion` every run" [S4]; a hook literally cannot call `AskUserQuestion` (that's an agent-loop capability, not available inside a synchronous hook subprocess) — so a hook's closest equivalent to "ask" is "don't deny, let Claude Code's own native permission system ask instead."
3. **A sentinel *file* and a project-scope preference *key* are not meaningfully different mechanisms here** — `<project>/.claude/bootstrap-prefs.json` gaining this key already **is** a sentinel: its presence (and value) is exactly as discoverable via `ls .claude/` as a bespoke marker file would be, and it comes with `/bootstrap-config`, schema validation, the generated `bootstrap-prefs.README.md` companion, and the four-state model for free. A hand-rolled sentinel (e.g. `touch .claude/allow-package-install`) would need its own presence-check code, its own documentation, and would not show up in `/bootstrap-config` or `--list` — a second, competing "is this feature on" convention alongside the one this repo already invested in.
4. **The real blocker isn't the mechanism, it's `askedBy`.** `test/bootstrap-prefs.test.js:2599-2630` requires every key's `askedBy` to resolve to a real `lib/scripts/*` file (bare name) or a real `lib/skills/<name>/SKILL.md` (`/slash-command` form) [S6]. `package-install-consent.js` lives in `lib/hooks/`, which **neither branch accepts**. Naming the hook file directly as `askedBy` would fail this test outright. This is a concrete, must-decide-before-implementing gap, not a detail to paper over.
5. **`consumer` has no "hook" category either.** `LEGAL_CONSUMERS = ['installer', 'skill']` is hardcoded in the test [S5], and the whole registry-doc-generation pipeline (`lib/scripts/README.md`'s two-table split, the generated companion's `installer`-then-`skill` grouping) assumes exactly these two. A new key consumed by a hook doesn't cleanly fit either label: it isn't asked by an installer script's own prompt, and it isn't read by a slash-command skill mid-session.
6. **Scope should be `project`, not `global` or `either`**, to match the user's actual complaint ("hard to create a new project", "update dependencies" — both project-scoped activities) without weakening the "no package enters this machine without consent" guarantee everywhere at once. `obsidian.plugins`/`obsidian.graphDefaults` already establish the `scope: project, values: "true | false"` precedent for exactly this kind of "local, deliberate, per-repo decision" [S6].

## Constraints

- **Must preserve today's default behavior exactly.** Every existing preference in this schema treats `unset` as "keep today's behavior" (documented explicitly for `gitCommit.autoPush`, `research.autoIngest`, etc. [S4]) — the new key's default must be `false` (deny, unconditional), so no existing user or repo experiences a behavior change until they explicitly opt in.
- **Must not weaken the headless-safety rationale.** The hook's own header explicitly rejects `permissions.ask` because headless runs (`/uat-auto-plus`, power-mode) have nobody to answer a prompt [S1]. A new `ask` value must not reintroduce that hang — since a hook-level "no decision" falls through to Claude Code's *own* permission-mode handling, a headless/bypass session already accepts "proceed without asking" for every other command it runs, so this is consistent, not a regression, for that mode. This should still be stated explicitly in the key's `detail` field, matching this schema's convention of documenting exactly why a default was chosen (see `gitCommit.autoPush`'s `detail` field for the pattern [S4]).
- **`askedBy` must resolve to something real**, per `test/bootstrap-prefs.test.js:2599` [S6] — the implementer must pick one of the paths in the Recommendation below, not invent a fourth resolution branch without also updating that test.
- **The deny message is the current "documentation" of the escape hatch** — `lib/hooks/README.md`'s own philosophy ("the deny message usually names the escape hatch, so the comment's job is why the trade was made" [S8]) implies the `deny()` call's `permissionDecisionReason` should mention the new opt-out inline, not just in `lib/hooks/README.md`.
- **No change to the Serena allowlist or the manager/subcommand tables** — this research is scoped to *whether* a matched install should still be denied, not to *what* counts as a matched install.

## Solution Comparison

| Criteria | A. New bootstrap-prefs key (project scope, `true\|false\|ask`) | B. Bespoke sentinel file (e.g. `.claude/allow-package-install`) | C. Widen the Serena allowlist / add more exceptions | D. Do nothing, document workaround better |
|----------|---|---|---|---|
| **Approach** | Hook reads a new `packageInstall.consent` key via `node ~/.claude/bootstrap-prefs.js --get ... --project .` (subprocess, matching every other consumer) | Hook does a synchronous `fs.existsSync()` check for a marker file/dir | Add more allowlisted package sources/managers by pattern | Leave the hook as-is; improve `lib/hooks/README.md` |
| **Pros** | Reuses `/bootstrap-config`, schema validation, generated docs, the four-state model; per-project; consistent with every other "should this thing prompt me" decision in the repo | Zero schema/test changes; trivially discoverable with `ls`; no `askedBy` problem at all | No new mechanism; solves *some* real friction (e.g. more MCP tooling) without a general bypass | Zero risk, zero effort |
| **Cons** | First hook-consumed key ever; forces the `askedBy`/`consumer` design decision now | A second, competing "is this on" convention outside `/bootstrap-config`; no `--list`/companion visibility; still needs its own docs and a presence-check helper | Doesn't solve the general "any new project's `npm install`" pain — allowlisting is inherently a per-package/per-manager patch, not a per-project trust decision | Does not address the user's stated problem at all |
| **Complexity** | Medium (schema entry + hook read + `askedBy` decision + doc/test updates) | Low-Medium (new helper, but no schema integration) | Low per exception, but grows unboundedly and never generalizes | None |
| **Dependencies** | None new — reuses `bootstrap-prefs.js` as a subprocess, exactly like every bash installer already does | None | None | None |
| **Codebase fit** | High — matches the stated design philosophy ("one binary every consumer goes through, so no prompt site keeps its own copy of a key's value list" [S4]) | Low — this repo has visibly standardized on `bootstrap-prefs.js` for exactly this kind of decision and has never used a bespoke sentinel for equivalent gates | Low — doesn't match the *shape* of the request (project-level trust, not package-level allowlisting) | N/A |
| **Maintenance** | One more schema entry; ordinary | A parallel mechanism to keep in sync with the "real" preference store conventions forever | Allowlist grows over time, needs periodic review | N/A |

## Recommendation

**Recommended approach: A (new project-scoped `packageInstall.consent` bootstrap-prefs key), not a bespoke sentinel file.** The preference-store mechanism already *is* a sentinel in every way that matters (a file whose presence/content is the signal), and building a second one would fragment discoverability (`/bootstrap-config` wouldn't show it) for no real gain — the only thing option A doesn't have going in is a settled answer to the `askedBy`/`consumer` gap, which needs a deliberate decision regardless of which storage mechanism is chosen, since it's about *documentation plumbing*, not about files-vs-JSON.

**Implementation outline:**

1. **Schema entry** (`lib/scripts/templates/bootstrap-prefs-schema.json`): `packageInstall.consent`, `scope: "project"`, `values: "true | false | ask"`, `default: false` (today's behavior — always deny, unchanged for everyone who never touches this). `detail` should explain all three states and explicitly restate the headless-safety reasoning so a future reader doesn't "fix" the `ask` value into something that could hang a bypass run.
2. **Hook change** (`lib/hooks/package-install-consent.js`): once `matchedInstall()` returns non-null (this only runs on the rare already-install-shaped command, so the extra subprocess cost is negligible), spawn `node ~/.claude/bootstrap-prefs.js --get packageInstall.consent --project <cwd>` synchronously, matching the pattern every bash installer already uses. On `false`/`unset`/any read failure → today's `deny()` exactly as now (preserves the "fails open toward the existing, safe default" contract — a broken preference read must never *grant* an install, only fall back to denying it, the same direction the file's current "Fails: open" note already accepts for its own internal errors). On `ask` → emit `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "defer", "permissionDecisionReason": "..."}}`, the officially-documented way to hand back to Claude Code's native permission handling (not an informal "omit the field" workaround). On `true` → emit `permissionDecision: "allow"`. Both need new shared `allow()`/`defer()` helpers in `lib/hooks/lib/command-parse.js`, mirroring the existing `deny()`.
3. **`askedBy` decision (make this explicitly, don't default into it):** given there's no scripted moment that naturally asks this (a brand-new project has no `.claude/bootstrap-prefs.json` yet when the user first hits the wall), the two realistic choices are (a) `askedBy: "/bootstrap-config"` — accurate today, since the only way to answer this is manually, or (b) add it as a **new, distinct project-scope question inside `setup-project.sh`/`update-project.sh`** (both already take `PROJECT_DIR`), following the `obsidian.plugins` precedent — asked once per project during `setup`/`update`, not mid-hook. Either choice is legitimate; **do not** invent a third `askedBy` resolution path (a `lib/hooks/` branch) without first updating `test/bootstrap-prefs.test.js`'s `LEGAL_CONSUMERS` and the `askedBy` resolution test, since that changes a contract the whole registry relies on.
4. **Update the deny message** to name the escape hatch inline (mirroring this repo's own stated hook-writing convention): something like *"...or set this project to stop asking: `node ~/.claude/bootstrap-prefs.js --set packageInstall.consent --value ask --project .`"*
5. **Update `lib/hooks/README.md`**'s `package-install-consent.js` section — the "Known friction, real and expected" framing should become "known friction by default, opt-out available per project," and the escape-hatches list at the top of the file (line ~53-54 convention) should gain this entry alongside the existing command-rephrasing ones.
6. **Tests**: extend `test/bootstrap-prefs.test.js`'s schema-shape tests for the new key; add hook-behavior tests (likely a new `test/package-install-consent.test.js` or an addition to an existing hook test file) covering `false`/`unset` (still denies), `ask` (no decision emitted), `true` (allow emitted), and a corrupted/missing prefs file (still denies, never allows).

**Risks and mitigations:**
- *Risk*: a user sets `true` once during a scaffold session and forgets, permanently disabling the consent gate for that repo. *Mitigation*: `project` scope (not global) already contains the blast radius to one repo; consider recommending `ask` over `true` as the documented "did you mean" default in any prompt/doc copy, since `ask` still requires an explicit interactive confirmation each time rather than silently trusting forever.
- *Risk*: the subprocess spawn on every matched install call adds latency. *Mitigation*: this only fires on already-rare install-shaped Bash calls (not every Bash call), and every existing bash-side consumer already pays this same subprocess cost per consult — consistent with, not worse than, the established pattern.
- *Risk*: extending `consumer`/`askedBy` to accommodate hooks properly (the "clean" fix) is a larger, cross-cutting change to a well-tested, deliberately strict registry contract. *Mitigation*: the `askedBy: "/bootstrap-config"` escape hatch (option 3a above) avoids this entirely and can ship first; a `consumer: "hook"` taxonomy addition can be a deliberate follow-up if/when a second hook wants the same treatment.

**Alternative if constraints change:** if a future need arises for *multiple* hooks to read preferences (not just this one), doing the `consumer: "hook"` taxonomy extension properly (updating `LEGAL_CONSUMERS`, the `askedBy` resolution test, and the README's table-generation grouping) becomes worth the one-time cost rather than accumulating several `/bootstrap-config`-asked-by keys that don't quite fit the `installer`/`skill` framing.
