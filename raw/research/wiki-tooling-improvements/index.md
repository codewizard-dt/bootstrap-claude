# Research: Improving the LLM Wiki tooling — what's new since the Karpathy gist

> This repo's `raw/llm-wiki.md` faithfully implements Andrej Karpathy's original LLM Wiki gist (published 2026-04-04 — three months before this research, not years). The ecosystem around that gist moved fast: at least four public projects (`claude-obsidian`, `ar9av/obsidian-wiki`, `MehmetGoekce/llm-wiki`, plus Claude Code's own **native Auto Memory** feature shipped by Anthropic) have independently converged on the same three gaps this repo's wiki does not yet cover — **session-to-session handoff (a "hot cache")**, **provenance/confidence tagging on claims**, and **concurrent-writer safety**. Separately, Claude Code itself gained a first-party memory system (the one *this very session* is using) that this repo's `wiki/` has no integration point for. The highest-leverage, lowest-cost next steps are: (1) add a `wiki/hot.md` session-handoff cache read at the start of every wiki operation, (2) formally activate the `confidence`/provenance frontmatter keys `wiki/conventions.md` already reserves-but-doesn't-use, and (3) write a short bridging convention so Claude Code's native Auto Memory (cross-session, cross-project) and this repo's wiki (per-project, git-versioned) don't silently duplicate or contradict each other. Heavier infrastructure (Mem0/Zep/Hindsight-style vector/graph memory layers, qmd local search) is available and mature but not yet justified at this repo's current wiki scale (empty scaffold, no ingested sources).

## Research Questions

1. What has changed in the public "second brain" / personal-knowledge-management ecosystem since Karpathy's LLM Wiki gist, and which of those changes are directly portable to this repo's wiki schema?
2. What do productized implementations of the *same* gist (built by other people, independently) do differently or additionally — and which of those differences look like genuine improvements rather than just different taste?
3. Has Claude Code itself (the harness this repo targets) grown built-in memory/context features since the gist, and does this repo's wiki architecture account for them?
4. What do dedicated agent-memory frameworks (Mem0, Zep/Graphiti, Letta/MemGPT, Hindsight, A-Mem) offer that a pure-markdown wiki doesn't — and is any of it worth adopting here, or is markdown-only still the right call at this repo's scale?
5. Concretely, what infrastructure, skill, hook, and prompting changes would most improve this repo's wiki tooling, ranked by cost vs. benefit?

## Current State (Codebase)

This repo (`bootstrap-claude`) is a **template/scaffolding package**, not a working wiki instance — `wiki/` in this repo is empty (no knowledge pages, no work items; confirmed via `wiki/index.md` placeholder text "_(none yet)_" across all sections). The actual wiki pattern lives in three places:

- **`raw/llm-wiki.md`** — a verbatim copy of Karpathy's gist (the idea file). Explicitly says "this document is intentionally abstract" and defers all tooling specifics to the implementer.
- **`wiki/conventions.md`** — this repo's own concrete implementation of the pattern: atomic pages, stable IDs, typed links (`rel::[[target]]`), and a **frontmatter namespace that already reserves but does not populate** `confidence`, `tier`, `last_verified`, `supersedes`, `superseded_by`, `scope` — explicitly called out as "populated later by overlays." The doc also explicitly name-drops the exact overlays this research was asked to investigate: *"so the heavier overlays (confidence scoring, knowledge lifecycle, hybrid search, A-Mem-style link discovery) can be added later as zero-migration add-ons."* This means the repo's own authors already anticipated this research direction and pre-wired the frontmatter for it — the gap is that no skill or hook actually populates these fields yet.
- **`lib/skills/wiki-*`** (9 skills: ingest, query, lint, archive, rotate-log, tidy) — implement Ingest/Query/Lint from the gist. No skill currently implements **session handoff** (a "what changed last time" cache) or **provenance tagging**.
- **`lib/hooks/`** — 14 hook scripts, overwhelmingly focused on **Serena-first code navigation enforcement** and a sophisticated **fail-open health-tracking system** (`serena-usage-tracker.js` classifies tool-level vs. transport-level failures, attempts one restart, auto-recovers). This fail-open pattern (assume healthy, only disable enforcement on confirmed transport failure, auto-restore on next success) is a strong, reusable design — and it's a template for how a future "wiki-lock" or memory-plugin health check should behave, but currently nothing in `lib/hooks/` touches `wiki/` file safety, wiki auto-commit, or memory injection.
- **Skills library is broad** (60+ skills: requirements, decisions, tasks, UAT, bugs, roadmaps, research, evals, security-audit, power-mode multi-agent orchestration) — meaning this repo already runs **heavy concurrent subagent activity** (`power-mode`, `tackle`, `now`) that could plausibly write to the same wiki family index or log file from multiple agents at once, which is exactly the failure mode other implementers have hit and started addressing with file locking (see Key Findings below).
- This session itself is running inside **Claude Code's native Auto Memory system** (see the `MEMORY.md`/per-type memory files described in this session's own system prompt) — a first-party feature that postdates this repo's wiki design and has zero cross-references to it anywhere in `CLAUDE.md` or the wiki schema.

## Key Findings

### 1. Claude Code shipped a first-party memory system that this repo's wiki doesn't acknowledge

Anthropic's Claude Code now ships **Auto Memory**: typed memory files (`user`, `feedback`, `project`, `reference` — the exact four types this session is instructed to use) stored under `~/.claude/projects/<hash>/memory/`, indexed by a `MEMORY.md`, auto-loaded at session start, and **specifically exempted from context compaction** — it survives summarization along with `CLAUDE.md` and any active skill [S17]. Anthropic's own official best-practices docs describe this as one of two now-standard patterns (the other being subagent delegation) for managing context across long sessions [S6]. Community write-ups independently describe the same architecture: "anything loaded from disk at startup comes back, anything that arrived through conversation gets summarized away" [S17], and note that **per-subagent** memory directories exist too (`.claude/agent-memory/<name>/MEMORY.md`, first 200 lines/25KB auto-injected) [S15].

This is architecturally adjacent to, but distinct from, this repo's wiki:
- **Auto Memory** is cross-project, un-versioned (lives outside the git repo, in `~/.claude/projects/`), small (200-line/25KB budget), and optimized for *behavioral* facts (how the user likes to work, standing feedback).
- **This repo's wiki** is per-project, git-versioned, unbounded in size, and optimized for *domain* knowledge (sources, decisions, tasks).

No file in this repo currently tells Claude Code how these two systems should divide responsibility, which risks two failure modes already documented in the wild: (a) duplicating the same fact in both places, or (b) a `feedback`-type Auto Memory entry silently overriding a `wiki/knowledge/` page's stated convention with no cross-reference. *(inference — no primary source ties this specific failure to this specific repo; the risk is inferred from the architecture, not observed)*.

### 2. Every independent reimplementation of the same gist converged on a "hot cache" / session-handoff file

At least three separate teams, building on the same Karpathy gist, independently added a mechanism this repo lacks: a small, always-read-first file summarizing "what happened last session."

- **`claude-obsidian`** (AgriciDaniel, MIT, 358+ GitHub stars) calls it `wiki/hot.md` — "At the end of every session, Claude updates `wiki/hot.md` with a compact context summary. The next session reads that file first. You never rebuild context." [S10, S11]. The file format is small and structured: `Last Updated`, `Key Recent Facts`, `Recent Changes` (created/updated/flagged), `Active Threads` [S12].
- **`MehmetGoekce/llm-wiki`** independently calls this an "L1/L2 cache architecture": "Auto-loaded rules in memory (L1) + deep knowledge in the wiki (L2)... the key insight Karpathy's gist does not mention" [S14].
- This maps directly onto Claude Code's own compaction behavior described above [S17] — a hot-cache file is essentially a hand-rolled version of what Auto Memory now does natively, but scoped to wiki-domain state rather than user-behavior state.

This repo's `wiki/log.md` is chronological (append-only, all history) but is not designed to be *read first* as a compact summary — a session resuming work has to scan or grep it. A `wiki/hot.md`-equivalent (or a "recent activity" section auto-maintained at the top of `wiki/index.md`) is the single most directly portable idea from this research.

### 3. Provenance/confidence tagging is a recurring, cheap addition other implementers already built — and this repo already reserved the frontmatter keys for it

- **`ar9av/obsidian-wiki`** tags every claim as `extracted` (default), `^[inferred]` (LLM synthesis), or `^[ambiguous]` (sources disagree), with a `provenance:` frontmatter block summarizing the mix per page, and a `wiki-lint`-equivalent that **flags pages drifting into mostly speculation** [S13].
- This is not a novel idea invented for AI wikis — it's the same instinct behind this research skill's own Phase 5 rule ("mark unsupported claims as *(inference — no primary source)*" rather than fabricating a citation), just formalized as page-level frontmatter instead of an inline note.
- `wiki/conventions.md` in this repo **already reserves** `confidence`, `tier`, `last_verified` as frontmatter keys "populated later by overlays... safe to ignore until then" [S2] — meaning this is a zero-migration addition: no existing file needs to change, only `/wiki-ingest` and `/wiki-lint` need new instructions to populate and check these fields.

### 4. Multi-writer safety for concurrent wiki edits is an active, only-partially-solved problem — relevant given this repo's heavy subagent orchestration

- `claude-obsidian` v1.7 added **per-file advisory locking** (`scripts/wiki-lock.sh`) specifically because "parallel ingest sub-agents acquire locks before writes" was previously a "latent multi-writer corruption hole" [S10, S20].
- A community report (r/hermesagent) describes a simpler ad-hoc pattern for two-agent concurrent edits: a YAML soft-lock (`locked: true` set/cleared atomically around the edit, with a 30-minute staleness override and a log entry on override) plus an append-only "Proposals" section so agents that can't coordinate can still both write without conflicting, since appends never collide [S21].
- `MehmetGoekce/llm-wiki`'s docs explicitly warn: "If you have multiple Claude sessions writing to wiki files simultaneously, concurrent edits can cause conflicts. Treat wiki files as a shared resource" [S14].
- Claude Code's own Agent Teams / worktree-isolation feature sidesteps this for *code* files by giving each subagent an isolated git worktree [S9-adjacent finding, from MindStudio], but this repo's `wiki/index.md`, family `index.md` files, and `wiki/log.md` are **shared append/edit targets by design** (every ingest touches the same index) — worktree isolation doesn't apply to a single logical file two agents both need to update.
- **This repo's own risk surface**: `power-mode` and `tackle` already run multiple concurrent subagents, and several wiki skills (`/wiki-ingest`, `/task-add`, `/decision-create`) all write to shared index files (`wiki/index.md`, family `index.md`s, `wiki/log.md`). If two subagents ever ran a wiki-writing skill concurrently, this is the exact failure mode others have already hit.

### 5. Local hybrid search (qmd) — already correctly identified in the gist as optional, and still the right call to defer

The original gist recommends `tobi/qmd` — a local CLI combining BM25 + vector + LLM re-ranking, with an MCP server interface — once a wiki "grows past a few hundred pages" [S1, S18]. Nothing has since obsoleted this recommendation; if anything qmd has matured (active development, MCP integration, documented "cuts token usage by 95%+" via retrieval instead of full-file reads) [S18]. But **this repo's actual wiki content is currently empty** — `wiki/index.md`-as-search is not yet a bottleneck anywhere in this template repo or (presumably) in any project it's been synced into. This is a "when you need it" addition, not a now addition.

### 6. Dedicated agent-memory frameworks (Mem0, Zep/Graphiti, Letta, Hindsight, A-Mem) are a different tool for a different job, not a wiki replacement

The 2025-2026 wave of memory frameworks is real and mature (Mem0 raised $24M, is AWS Agent SDK's default memory provider, 186M API calls in Q3 2025 [S7, S8]; Zep's Graphiti adds temporal knowledge graphs on Neo4j [S7]; Letta/MemGPT's own August 2025 benchmark found a plain-filesystem agent beat Mem0's graph variant on long-context recall, arguing "agents are post-trained to be good at iterative file search, so specialized memory systems add little" [S7] — a notable data point *against* over-engineering memory infra). Hindsight specifically targets the exact gap flagged in Finding 4 — cross-subagent shared memory in Claude Code — via a hooks + MCP plugin giving every subagent read/write access to one memory bank instead of N siloed `MEMORY.md` files [S15, S16].

All of these are optimized for **conversational/episodic recall at scale** (chat histories, user preferences across sessions) — a genuinely different problem from **curated, versioned, cross-referenced domain knowledge**, which is what this repo's wiki is for. Letta's own finding above is direct evidence that "just use files, well-organized" is a defensible, not backwards, choice at this repo's scale. The right time to reach for one of these is if/when a specific concrete pain point emerges (e.g., subagents in `power-mode` genuinely losing shared context across a long multi-wave run) — not preemptively.

## Constraints

- **Any change must be additive, not a rewrite.** `wiki/conventions.md` was explicitly written to allow exactly this kind of overlay ("zero-migration add-ons") — new frontmatter keys, new skill instructions — without touching existing files or breaking the "raw/ is immutable" and "atomic pages" rules already in force.
- **This is a template repo, not a live wiki** — changes here are to the *scaffold* (`lib/scripts/templates/wiki/`, `lib/skills/wiki-*`, `lib/hooks/`) that gets synced into *other* projects' `wiki/` directories, not to this repo's own (empty) `wiki/`. Any recommendation must be implementable as a skill/hook/template change, not a one-off wiki edit.
- **Copy-once vs. always-refresh semantics already exist** (`sync-wiki-scaffold.sh`) — new template files (e.g., a `hot.md` stub) need to be classified into one of these two buckets correctly, or updates will either clobber project-owned content or never propagate fixes.
- **No new required infrastructure/dependencies.** The gist's own philosophy — and this repo's existing zero-dependency wiki (Serena, Brave, Context7 aside) — argues against introducing a vector DB, graph DB, or SaaS memory layer as a *default*. Anything heavier should be optional, documented, and opt-in (mirroring how `qmd` is already framed as optional in `raw/llm-wiki.md`).
- **Multi-agent write safety must not slow down the common (single-agent) case.** A locking mechanism modeled on the existing fail-open Serena health-tracking pattern (`lib/hooks/lib/serena.js`) — enforce by default, degrade gracefully on failure, auto-recover — is the established idiom in this codebase and should be reused rather than inventing a new failure-handling philosophy.

## Recommendation

**Adopt A, B, and D now; hold C and E until a concrete trigger.**

1. **A — hot cache** and **D — the bridging doc** are strict no-regret wins: no new dependencies, no schema migration, and both close a gap that Claude Code's own native features (Auto Memory, compaction-survival) and every other public reimplementation of this exact gist have already converged on independently. Do these together, since the hot-cache file is itself a candidate for the "what belongs where" line D draws (hot cache = wiki-domain session state; Auto Memory = cross-project user/feedback state).
2. **B — provenance tagging** is next: it activates frontmatter this repo's own conventions doc already promised ("zero-migration add-ons"), and gives `/wiki-lint` a concrete, checkable signal instead of relying on the LLM's judgment alone to catch drift into speculation.
3. **C — multi-writer locking** should be built, but only scoped to the specific shared files that concurrent skills actually touch (`wiki/index.md`, each family `index.md`, `wiki/log.md`) — not every wiki page, since most pages are written by exactly one skill invocation at a time. Model it directly on the existing `serena.js` fail-open pattern (enforce by default, one-time degrade notice on confirmed failure, auto-recover) rather than inventing new semantics. This is worth doing given `power-mode`/`tackle` already run concurrent subagents against a repo that (per this same research skill's own instructions) requires touching shared index files on every wiki operation.
4. **E — a dedicated memory framework (Hindsight, Mem0, etc.)** should be treated as a documented *option*, not a default: add a short note in `raw/llm-wiki.md`'s "Optional: CLI tools" section (alongside the existing `qmd` mention) pointing at Hindsight specifically for the cross-subagent-memory-sharing use case, but do not wire it into the template's default skill/hook set. Letta's own benchmark finding — that a well-organized filesystem approach can *beat* a dedicated graph-memory framework on long-context recall [S7] — is direct evidence this restraint is well-founded, not conservative-for-its-own-sake.

**Implementation outline** (for A/B/D, as a follow-on task):
- Add `wiki/hot.md` to `lib/scripts/templates/wiki/` (copy-once — project-owned once created) with the format Karpathy-derivative projects converged on: `Last Updated`, `Key Recent Facts`, `Recent Changes`, `Active Threads` [S12].
- Update `/wiki-ingest`, `/task-add`/`task-update`, `/decision-finalize`, and any skill that changes wiki state to append/refresh `wiki/hot.md` as a final step.
- Update `/primer` (already exists specifically to "refresh codebase context via Serena memories") to read `wiki/hot.md` first, before Serena memories.
- Add a `confidence: extracted | inferred | ambiguous` frontmatter convention to `wiki/conventions.md`'s existing (currently unused) "Reserved keys" section, and teach `/wiki-ingest` to set it and `/wiki-lint` to flag pages that are mostly `inferred`/`ambiguous` with no `extracted` claims.
- Add a short "Auto Memory vs. this wiki" subsection to `CLAUDE.md`'s LLM Wiki section: Auto Memory owns cross-project user/feedback facts; the wiki owns per-project domain/source/decision knowledge; never write the same fact to both.

**Risks and mitigations**:
- *Hot cache goes stale / becomes another maintenance burden* → mitigate by keeping it small (the gist's own precedent caps it at ~500 words [S12]) and regenerating it fully each time rather than appending, so staleness self-corrects.
- *Provenance tagging gets skipped under time pressure* → mitigate by making `/wiki-lint` actively check for it (a missing `confidence` field on a newly-ingested page is itself a lint finding), not just documenting the convention and hoping.
- *Locking adds friction to the common single-agent case* → mitigate by making the lock acquire/release near-instant (a file touch/delete, per the community pattern [S21]) and only wrapping the specific shared-index write, not the whole skill invocation.

**Alternative if constraints change**: if a future project synced from this template accumulates enough subagent-driven wiki writes that ad hoc locking proves insufficient (repeated corruption, not just theoretical risk), revisit Hindsight or a similar shared-memory-bank MCP as the concurrency layer instead of hand-rolled locks — at that point the maintenance cost of running dedicated memory infra will be justified by an observed, not hypothetical, problem.
