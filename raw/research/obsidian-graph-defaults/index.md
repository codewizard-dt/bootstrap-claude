# Research: Obsidian Graph View Styling, Productivity Patterns, and Shippable Wiki Defaults

> Graph-view color groups are a **native, zero-plugin** Obsidian feature stored in plain JSON (`.obsidian/graph.json`) and driven by the same search syntax (`path:`, `tag:`, `file:`, `line:`) used everywhere else in Obsidian — which means this repo can hand-author a `colorGroups` template keyed to its own stable `wiki/knowledge` vs `wiki/work/*` vs `raw/` taxonomy and have every new project's graph view arrive pre-styled, with no new plugin dependency and no per-project detection logic needed. Community plugins (Graph Styler, Auto Tag Graph Colors) exist for *automatic*, vault-agnostic styling and are worth flagging as opt-in layers, but they solve a problem this repo doesn't have — its folder taxonomy is already fixed and known at scaffold time. Broader Obsidian productivity practice (Zettelkasten/PARA/MOC communities) converges on one relevant lesson for this wiki: let navigation structure (MOCs, in this repo's case `wiki/index.md` + family `index.md` files) emerge from the graph rather than trying to hand-design it — which this repo already does.

## Research Questions
- How does Obsidian's graph view actually get its visual configuration (which files, what schema, plugin vs. native)?
- Which community plugins extend or automate graph-view styling, and how do their config mechanisms differ from native `colorGroups`?
- How do other people and projects structure and use Obsidian to maximize productivity (methodologies, vault templates, defaults-setting patterns)?
- Given `.obsidian/` is gitignored per project (confirmed prior research, [[obsidian-wiki-linking]], [[obsidian-setup-automation]]), what does "shipping defaults into new projects" concretely mean, and how does it fit this repo's existing template/sync conventions?
- What is the lowest-risk, highest-leverage next step to make this repo's own `wiki/knowledge` vs `wiki/work/*` vs `raw/` structure visually legible in the graph view out of the box?

## Current State (Codebase)

- **`.gitignore`** excludes `.obsidian/` (line 7) — confirmed directly. Any per-vault Obsidian configuration is machine-local by design; this repo has never committed shared Obsidian config, and both prior research reports on this topic ([[obsidian-wiki-linking]], [[obsidian-setup-automation]]) explicitly built their recommendations around that constraint [S4].
- **`lib/scripts/install-obsidian.sh`** already establishes the exact mechanism "shipping defaults into new projects" needs: it is a project-scoped script, gated by sticky preferences (`obsidian.installApp` global scope, `obsidian.plugins` project scope via `prompt_yn_sticky`/`prefs_get`), that writes files directly into `<vault>/.obsidian/` — three community plugins (Dataview, Graph Link Types, Breadcrumbs) fetched from GitHub Releases and dropped into `.obsidian/plugins/<id>/`, with `<id>` read authoritatively from each release's own `manifest.json` rather than assumed from the repo name, and enabled via an idempotent read-modify-write of `.obsidian/community-plugins.json` [S2]. This script is the natural home for a new "write default `graph.json`" step — no new install pattern needs inventing.
- **`lib/scripts/templates/`** already hosts the repo's copy-once template convention (`wiki/hot.md`, `wiki/log.md`, `wiki/index.md`, `CLAUDE-wiki.md`, `settings-hooks.json`, etc.), synced into new projects by `sync-wiki-scaffold.sh` and `install-global.sh`, with an established "copy-once for project-owned files, always-refresh for template-owned files" rule. There is currently **no `.obsidian/*` entry anywhere in this templates directory** — graph/appearance/workspace defaults would be a new leaf under this same pattern, not a new mechanism [S3].
- **`wiki/knowledge/entities/tools/obsidian.md`** and **`wiki/knowledge/sources/obsidian-setup-automation.md`** record this repo's existing understanding: Obsidian is explicitly the "human-side viewer" only, never a hard dependency, and prior research already flagged that `raw/llm-wiki.md` names the graph view for spotting hubs/orphans but that "nothing about setup automates getting to that state; it's manual today" [S5, S6]. That gap — graph view is *recommended* in the pattern spec but nothing configures it — is exactly what this research closes.
- **Prior research explicitly scoped itself to plugin binaries only**, not native graph/appearance config: "`.obsidian/plugins/`, `.obsidian/community-plugins.json`, the Obsidian app itself... Nothing here should try to make plugin configuration shared/committed" [S6]. This is not a contradiction of that research — it's an adjacent, previously-unexamined surface (native `graph.json`, which requires zero plugins and is a different design question than "should we vendor third-party compiled JS into git").

## Key Findings

1. **`.obsidian/graph.json` is a plain, hand-editable JSON file, and `colorGroups` requires no plugin at all.** Two real-world examples confirm the exact shape: `{"collapse-color-groups": true, "colorGroups": [], "collapse-forces": true, "centerStrength": ..., "repelStrength": ..., "linkStrength": ..., "linkDistance": ..., "scale": ..., ...}` [S7, S8]. A `colorGroups` entry is `{"query": "<search string>", "color": {"a": 1, "rgb": <int>}}` — confirmed by a user's own Python automation that read the file with `json.loads`, appended `colorGroups` entries programmatically, and wrote it back with `json.dumps`, with Obsidian picking up the change on next open [S9]. This is the single most important finding: **styling the graph by folder/tag is a JSON-authoring problem, not a plugin-installation problem.**
2. **The query syntax for a color group is Obsidian's ordinary search syntax** — `path:private` (folder-based), `tag:#cool` (tag-based), `file:journal` (filename-based), combinable with boolean `OR`/`AND` (e.g. `tag:(#cool OR #search OR #moc)`) [S10]. Official docs confirm the mechanism (Settings → Graph → Groups → "New group" → type a search term → assign a color) but do not themselves enumerate the query grammar — that lives in Obsidian's general Search syntax, and the community sources above are the concrete, verified reference [S11].
3. **Three other `.obsidian/*.json` files exist alongside `graph.json`, each with a distinct, documented role**: `app.json` (core editor/file-handling behavior), `appearance.json` (theme, CSS snippets enabled, font, translucency), and `workspace.json` (pane/sidebar layout, restored on vault open — auto-written by Obsidian itself, "manual editing is rarely needed") [S12]. Of these, only `graph.json` and `appearance.json` are realistic candidates for a shipped default; `workspace.json` is explicitly layout state that Obsidian regenerates and fights with if hand-edited.
4. **Community plugins for graph styling solve a different problem than this repo has: unknown/arbitrary vault structure.**
   - **Graph Styler** (`moonweave/obsidian-graph-styler`, MIT) applies one-click aesthetic presets — it inspects the vault, "finds your most-used folders and assigns the preset's palette to them (up to 4)... No folders? It falls back to your most-used tags," writes the result into native `graph.json` color groups (so it stays inspectable/editable afterward) plus a CSS glow snippet into `.obsidian/snippets/`, and explicitly backs up the original `graph.json` first [S13, S14]. Its entire value proposition is *automatic* folder/tag detection for vaults whose structure isn't known in advance.
   - **Auto Tag Graph Colors** (`Trisko06/auto-tag-graph-colors`) auto-assigns a stable, distinct color to every tag with zero configuration, including "heat coloring by connection count," and cleanly removes every group it created if the plugin is disabled (preserving manually-added groups) [S15].
   - **Style Settings** (`community-archive/obsidian-style-settings`) is a general CSS-variable-exposure plugin, not graph-specific, but is the mechanism several graph-color-by-tag CSS snippets rely on (a `/* @settings */` YAML block in a CSS snippet exposes color pickers in Obsidian's own Settings UI) [S16].
   - **Colored Tags** and CSS-snippet-based approaches (e.g. per-tag `--tag-color` variable overrides) are the lighter-weight alternative to a full plugin when only tag-node color (not graph *group* color) is the goal [S16 discussion thread].
   - **Graph Link Types** (already installed by this repo's `install-obsidian.sh`) is complementary, not competing: it labels/colors *edges* by reading Dataview-indexed inline fields (this repo's `rel::[[target]]` convention), whereas `colorGroups`/Graph Styler/Auto Tag Graph Colors color *nodes*. Both together give a fully legible graph: node color = which family/domain a page belongs to, edge label = what kind of relationship connects two pages.
5. **This repo's own taxonomy is already stable and known ahead of time** (`wiki/knowledge/{sources,concepts,entities}`, `wiki/work/{tasks,bugs,decisions,roadmaps,requirements,uat}`, `raw/`) — every project gets the identical scaffold from `sync-wiki-scaffold.sh`. That means the auto-detection plugins (Graph Styler, Auto Tag Graph Colors) are solving a problem this repo doesn't have; a **hand-authored `colorGroups` template keyed to these exact paths is strictly more precise and requires zero new plugin dependency**, consistent with this repo's stated preference (per [[obsidian-setup-automation]]) to keep community-plugin installs opt-in and minimal given they "execute arbitrary JS with full vault read/write access and no granular permission system."
6. **Vault-template projects on GitHub validate the "ship a documented diff from Obsidian's defaults" pattern this repo would be extending.** `andrewmcodes/obsidian-beginner-vault-template` explicitly documents, in a table, every editor/file-handling setting it changes from stock Obsidian defaults, and ships zero community plugins by default — the philosophy is "good native defaults first, plugins are the user's opt-in choice later" [S17], which matches this repo's own posture (`obsidian.plugins` is a separate opt-in gate from anything that would just be pre-authored config).
7. **Sharing `.obsidian/*` config across a git-tracked vault is a well-trodden, if inconsistently-solved, community problem** — the common pattern is *not* "un-ignore all of `.obsidian/`" but selectively un-ignoring specific files: `.obsidian/*` ignored by default, then `!.obsidian/app.json`, `!.obsidian/appearance.json`, `!.obsidian/graph.json` etc. added back explicitly [S18], or the inverse (ignore `cache*`/`workspace*`/plugin binaries, keep `plugins/*/data.json`) [S19]. This repo doesn't need to change its own `.gitignore` policy (it isn't committing `.obsidian/` at all, and shouldn't — see Constraints) — but it confirms that "some `.obsidian/*.json` files are meant to be shared/templated, others are inherently machine-local" is the correct mental model, and `graph.json`/`appearance.json` sit on the "templatable" side of that line while `workspace.json`/`cache*` sit on the "machine-local" side.
8. **Broader Obsidian productivity practice, from Zettelkasten/PARA communities, converges on "let structure emerge, don't over-engineer it upfront."** A 2025 practitioner guide is explicit: "Don't create MOCs upfront. Let them emerge naturally... Building MOCs too early creates structure for structure's sake, which is the opposite of what Zettelkasten is for" [S20]. This is a direct validation of this repo's existing design — `wiki/index.md` and family `index.md` files already are lightweight MOCs that get updated on every ingest/status-change rather than hand-curated in advance — and argues against over-investing in bespoke per-project graph taxonomy beyond the stable top-level one identified in Finding 5.
9. **Dataview remains the single plugin most cited across every productivity/PKM source as the actual force-multiplier**, not graph styling — used for dynamic query tables over frontmatter (exactly what `raw/llm-wiki.md` already anticipates per prior research) [S6]. This reinforces that graph-view styling is a *legibility* improvement (see the wiki's shape at a glance), while Dataview query blocks are the *productivity* improvement (act on the wiki's data) — both were already identified as low-risk opt-ins by [[obsidian-setup-automation]], but only the plugin-*install* half of that recommendation has since shipped (`ROADMAP-006`, per recent commit history); the query-*authoring* half (actual `​```dataview` blocks in family `index.md` files) has not.

## Constraints

- `.obsidian/` stays gitignored — any shipped default is a **generated, machine-local file written at setup/update time**, never a committed shared config. This matches the existing `install-obsidian.sh` model exactly.
- Community plugins carry real supply-chain risk (arbitrary JS, no permission model) — any *new* plugin recommendation (Graph Styler, Auto Tag Graph Colors) must go through the same sticky opt-in gate already used for Dataview/Graph Link Types/Breadcrumbs, not a silent default. Native `graph.json` styling has no such risk since it ships zero code, only data.
- A shipped `graph.json` must **not clobber a user's already-customized graph settings** — the safe pattern (mirroring Graph Styler's own behavior of backing up the original file first [S13], and this repo's own "copy-once for project-owned files" convention [S3]) is: write only if the file doesn't already exist, or merge only the `colorGroups` key rather than overwriting the whole file.
- The `colorGroups` query syntax is path/tag/file-string matching, not a schema-validated reference to this repo's actual family list — if `wiki/work/tasks` gets renamed or a new family is added, the shipped `graph.json` template needs the same manual-update discipline as any other template file, there's no dynamic binding.
- `appearance.json` (theme/CSS snippets) and `workspace.json` (pane layout) are lower-value/higher-risk defaults to ship: theme is a matter of personal taste with no "correct" default for this repo's purposes, and `workspace.json` is explicitly runtime layout state Obsidian rewrites constantly — templating it would likely just get silently overwritten on first open.

## Recommendation

**Ship option A first — a hand-authored `.obsidian/graph.json` `colorGroups` template — as the immediate, zero-dependency win**, then treat B and C as optional follow-on opt-ins layered behind the existing plugin-consent gate, not a replacement for A.

**Implementation outline:**
1. Add `lib/scripts/templates/obsidian/graph.json` (or a `colorGroups`-only fragment) with entries such as `path:"wiki/knowledge"`, `path:"wiki/work/tasks"`, `path:"wiki/work/bugs"`, `path:"wiki/work/decisions"`, `path:"wiki/work/roadmaps"`, `path:"wiki/work/requirements"`, `path:"wiki/work/uat"`, `path:"raw/"` — each with a distinct color, following the confirmed `{"query": "...", "color": {"a":1,"rgb":<int>}}` shape [S7, S9].
2. Extend `lib/scripts/install-obsidian.sh` with a new function (mirroring `_install_obsidian_plugin`'s "warn and skip, never abort" discipline) that copies this template into `$PROJECT_DIR/.obsidian/graph.json` **only if that file does not already exist** — new sticky preference key, e.g. `obsidian.graphDefaults` (project scope, same selector convention as `obsidian.plugins`), or fold it into the existing `obsidian.plugins` prompt if it's judged not worth a second question.
3. Document the query-syntax mechanism (`path:`, `tag:`, boolean `OR`) in whichever `wiki/guides/` page already covers Obsidian setup, so users know how to extend the template themselves as their vault grows beyond the default families.
4. Treat Graph Styler / Auto Tag Graph Colors as a later, separate opt-in decision — add them to the existing plugin array only if/when a user-facing need for automatic (vs. hand-templated) styling actually surfaces, consistent with this repo's demonstrated "don't install what nothing has asked for yet" discipline in [[obsidian-setup-automation]].
5. Separately (lower priority, not blocking the above): author 2-3 example `​```dataview` query blocks in family `index.md` templates (e.g. a `TABLE status FROM "wiki/work/tasks"` block) — this is the still-unactioned "productivity" half of prior research's recommendation, distinct from the graph-view "legibility" half this report focuses on.

**Risks and mitigations:**
- *Clobbering a user's customized graph.json* → write-if-absent only, never overwrite (mirrors Graph Styler's own backup-first discipline).
- *Template drift if the wiki taxonomy changes* → treat `graph.json` as a template-owned file like `wiki/conventions.md`, refreshed alongside taxonomy changes, not "copy-once forever."
- *Query strings silently going stale* (e.g. a family folder gets renamed) → low-severity, purely cosmetic failure mode (the color group just stops matching anything); no functional breakage.

**Alternative if constraints change:** if this repo later wants graph styling to *actively adapt* as users add non-wiki content to their vault (content Graph Styler and Auto Tag Graph Colors are actually built for), promote option B or C from "optional opt-in" to "default-recommended," but that's a materially different bet (trusting a small 2026-vintage community plugin) than shipping static JSON.
