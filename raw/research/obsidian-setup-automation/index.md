# Research: Automating Obsidian + Plugin Setup in the Bootstrap Scripts

> Both halves are automatable with zero manual steps, and both fit the repo's existing "guarded, opt-in, sticky-preference" install pattern used for MCPs and optional guides — no new pattern needs to be invented. Installing the Obsidian **app** is a one-line native-package-manager call per OS (`brew install --cask obsidian` / `winget install -e --id Obsidian.Obsidian` / `flatpak install flathub md.obsidian.Obsidian`). Installing the **plugins** (Dataview, Graph Link Types, Breadcrumbs) needs no app and no GUI at all — Obsidian's own plugin loader is just three files per plugin (`manifest.json`, `main.js`, optional `styles.css`) dropped into `<vault>/.obsidian/plugins/<id>/`, with `<vault>/.obsidian/community-plugins.json` listing which are enabled; a setup script can fetch these directly from each plugin's GitHub Releases API. The genuinely new judgment call is which existing skill workflows should change to benefit — the honest answer is: `/wiki-lint`'s and `raw/llm-wiki.md`'s already-recommended graph-view usage improves for free with zero skill-file edits (relation labels just appear), but `/task-audit`'s dependency graph does **not** benefit automatically — its dependency block is a bespoke blockquote format, not the `rel::[[target]]` convention these plugins read, so wiring it up is a separate, deliberate follow-on task, not a side effect of installing plugins.

## Research Questions

1. Can Obsidian itself be installed automatically, cross-platform, in a way that fits this repo's existing guarded/non-fatal install pattern?
2. Can the three plugins (Dataview, Graph Link Types, Breadcrumbs) be installed automatically without a running Obsidian instance or manual GUI steps?
3. What does "opt-in but highly recommended" look like concretely, given the preference-gating mechanisms this repo already has?
4. Which existing skills would materially improve if these plugins were present, and which would need their own follow-on work to actually benefit?
5. Where does this slot into `setup-project.sh` / `update-project.sh`'s existing sequence?

## Current State (Codebase)

- **Zero existing automation** references Obsidian anywhere under `lib/` — confirmed by an exhaustive pattern search; the only two hits are `mermaid-flowchart/SKILL.md` mentioning Obsidian as a Mermaid-rendering viewer, unrelated to setup.
- **The guarded-install pattern already exists and is directly reusable.** `lib/scripts/install-mcps.sh`'s `register_optional_mcp()` wrapper (and its bespoke `_add_playwright`/`_add_brave` adders) is exactly the shape needed: check-if-already-installed short-circuit → in interactive mode, a sticky yes/no prompt via `prompt_yn_sticky <pref-key> <selector> "<prompt>"` (`lib/scripts/lib.sh:251`) → install via native tooling → never abort the parent script on failure (`register_optional_mcp`'s callers are wrapped so a failure only warns). `_add_playwright` in particular already does "detect OS, install a native binary via a package manager, wire it up, warn instead of crash" for a GUI-adjacent macOS tool (a launchd agent), which is the closest existing precedent to "install a desktop app."
- **The sticky-preference mechanism is schema-driven and already has a bundled-optional-item precedent.** `sync-wiki-scaffold.sh`'s `OPTIONAL_GUIDES` loop (`lib/scripts/sync-wiki-scaffold.sh:80-133`) is the closest precedent for "an opt-in-but-recommended bundle": a stored `true` delivers on every run (including non-interactive), a stored `false` is silently honored, and an unset/`ask` value prompts once via `prompt_yn_sticky "guides.$guide" "$PROJECT_DIR" "..."`. `lib/scripts/templates/bootstrap-prefs-schema.json` documents every existing key in this same shape (`scope`, `consumer`, `summary`, `detail`, `values`, `default`, `askedBy`) — any new `obsidian.*` keys should follow this exactly, including a `dynamic: true` flag if per-plugin keys are used (mirroring `guides.*`).
- **`run_project_sync()`** (`lib/scripts/lib.sh:149-178`) is the single call site both `setup-project.sh` and `update-project.sh` funnel through: install-global (skills/hooks) → MCPs (guarded) → wiki scaffold + gitignore → MCP guide build → Serena bootstrap. A new Obsidian step slots naturally between "Syncing wiki scaffold" and "Building MCP tools guide" — after the scaffold exists (so there's a vault worth configuring) and before the guide-build step, which doesn't depend on it.
- **`raw/llm-wiki.md`** already tells the human to use Obsidian's graph view to spot hubs/orphans and names Dataview as the tool for "dynamic tables and lists" over frontmatter — but nothing about setup automates getting to that state; it's manual today.
- **`.gitignore`** excludes `.obsidian/` — confirming any Obsidian configuration this automation writes is inherently machine-local, exactly like the existing MCP registrations in `~/.claude.json` and the Playwright launchd agent. This constrains the design: nothing here should try to make plugin config shared/committed.
- **`/task-audit`'s dependency graph is NOT built on the `rel::[[target]]` typed-link convention.** `lib/skills/task-audit/SKILL.md` (Step 2e) parses a bespoke blockquote immediately after each task's title:
  ```markdown
  > **Depends on**: [002-foo](002-foo.md), [003-bar](003-bar.md)
  > **Blocks**: [008-baz](008-baz.md)
  > **Parallel-safe with**: [005-qux](005-qux.md), [006-quux](006-quux.md)
  ```
  This is plain markdown links inside a blockquote, not `depends_on::[[TASK-002]]` inline fields. Dataview/Breadcrumbs cannot read this format out of the box — a real constraint on "which skills benefit," addressed in Key Findings below.
- **This research builds directly on `raw/research/obsidian-wiki-linking/index.md`** (this repo's prior research on the same topic), which already established: the `rel::[[target]]` vocabulary (`derived_from`, `supersedes`, `implements`, `uses`, `depends_on`, `contradicts`, `relates_to`, etc.) is Dataview's native inline-field syntax; zero `​```dataview` query blocks exist in the repo today; Graph Link Types and Breadcrumbs both consume that existing syntax unmodified. That prior report's entity pages (`wiki/knowledge/entities/tools/{obsidian,dataview,graph-link-types,breadcrumbs-plugin}.md`) were ingested into the wiki earlier in this session and are treated here as background, not re-derived.

## Key Findings

1. **Installing Obsidian itself is a single, well-documented command per platform, all silent/non-interactive-capable.** macOS: `brew install --cask obsidian` [S9]. Windows: `winget install -e --id Obsidian.Obsidian` — the winget manifest itself declares `InstallModes: [silent]`, i.e. it supports a fully unattended install [S10]. Linux: `flatpak install -y flathub md.obsidian.Obsidian` is the officially verified, auto-updating path recommended across every Linux install guide found; `.deb`/AppImage/Snap all work too but don't self-update the way Flatpak does, making Flatpak the better default for a script that shouldn't need to be re-run to pick up security fixes [S11]. All three are guardable exactly like `_add_playwright`'s `npm install -g @playwright/mcp` step: run the command, check the exit code, `echo "WARNING: ... continuing"` on failure rather than aborting.

2. **Installing the plugins requires no running Obsidian process and no GUI — it's just files on disk, read the next time the vault opens.** Obsidian's own plugin-releases repo documents the mechanism directly: "Obsidian will read the list of plugins in `community-plugins.json`... Obsidian will download `manifest.json`, `main.js`, and `styles.css` (if available), and store them in the proper location inside the vault" [S12]. Community how-tos independently confirm the exact manual equivalent — download those three files from a plugin's GitHub Releases page, place them in a folder under `<vault>/.obsidian/plugins/` [S8, S9-repo, S11-reddit]. `community-plugins.json` itself is a real, stable, cross-platform file — an Obsidian Forum thread from a user troubleshooting exactly this file confirms both its existence and its role tracking which plugins are enabled [S13]. **The one detail every source stresses**: the folder name under `.obsidian/plugins/` must exactly match the `id` field inside that plugin's own `manifest.json` — so a robust installer downloads `manifest.json` *first*, reads its `id`, and only then names the directory and fetches `main.js`/`styles.css`, rather than assuming the GitHub repo name matches the plugin id.

3. **This is exactly a `curl`-from-GitHub-Releases-API job, structurally identical to how this repo already fetches other tooling.** The pattern: `GET https://api.github.com/repos/<owner>/<repo>/releases/latest` → find the `manifest.json`/`main.js`/`styles.css` asset URLs in the response → download each → write `community-plugins.json` (create `["dataview"]` if absent, else merge-if-missing — the same small idempotent JSON-merge shape `install-mcps.sh`'s `_disable_project_playwright_locally` already uses via an inline `node -e '...'` block for a different file). No BRAT (Beta Reviewer's Auto-update Tool) is needed for this: BRAT is a *GUI-side* convenience plugin that itself has to be manually bootstrapped inside a running Obsidian instance before it can fetch anything [S14] — it solves a different problem (a human wanting beta-channel plugins from inside the app) and is not a scripting primitive.

4. **"Opt-in but highly recommended" maps cleanly onto the existing `prompt_yn_sticky` + schema-key pattern, and the repo has both a single-toggle precedent and a per-item precedent to choose from.** `mcp.playwright` / `mcp.braveSearch` are single sticky yes/no toggles per tool [S1]. `guides.*` is a *dynamic* per-item key (`guides.evals-framework.md`, `guides.type-checking-templates`) — one prompt, one remembered answer, per item [S3]. Given the three plugins are being pitched here as one cohesive "typed-link enhancement" bundle (Dataview is a hard prerequisite for the other two), a single bundled prompt (`obsidian.plugins`) with one sticky answer is the better fit than three separate prompts — it matches how they're actually being recommended (together) rather than how MCPs are recommended (each independently useful). The app-install question (`obsidian.installApp`) is a separate, independent toggle, since a user might want the plugins pre-staged in the vault without wanting Claude Code to install a GUI app on their machine at all.

5. **Which skills would materially improve, honestly assessed:**
   - **`/wiki-lint` and `raw/llm-wiki.md`'s own graph-view guidance improve with zero skill-file changes.** `raw/llm-wiki.md` already tells the user "Obsidian's graph view is the best way to see... which pages are hubs, which are orphans" — that's already how orphan-page detection is meant to be visually cross-checked by a human. Installing Graph Link Types makes every existing `rel::[[target]]` edge (already written by `/wiki-ingest`, `/wiki-lint`, etc.) show its relation label directly on the graph. This is a pure improvement to an already-recommended workflow, with no skill file needing to change.
   - **`/task-audit` does NOT automatically improve** — per Current State above, its dependency block is a bespoke blockquote, not `depends_on::[[TASK-NNN]]`/`blocks::[[TASK-NNN]]` inline fields. Breadcrumbs *could* visualize task dependencies live in Obsidian, but only after either (a) `/task-audit`'s Step 2e is changed to also emit typed-link lines alongside (or instead of) the blockquote, or (b) Breadcrumbs is configured with a custom regex source matching the existing blockquote — Breadcrumbs supports custom naming-scheme sources exactly for cases like this [prior research, S10]. This is a real, identifiable follow-on task — not something automatic plugin installation delivers on its own, and it should not be silently bundled into the setup-script work.
   - **`/wiki-query`, `/decision-create`, and family `index.md` files are natural homes for optional Dataview query blocks** (e.g., a `​```dataview` table listing all `wiki/work/decisions/` by status) — but per the prior research's own recommendation, these should be added deliberately as documentation/examples in a guide, not auto-generated by the setup script, since `wiki/conventions.md`'s `index.md` contract ("active items only, as a flat bullet list") shouldn't be silently changed by an installer.
   - **`wiki-dashboard-server.js` should NOT be replaced or deprioritized.** It renders `wiki/work/` over plain HTTP with zero local app dependency, which makes it strictly more portable than any Obsidian-based view for CI, remote/headless agents, or teammates without Obsidian installed. The two are complementary — dashboard for headless/shared access, Obsidian+plugins for the human's own local exploration — not competing options.

## Constraints

- Community plugins execute arbitrary JavaScript with full vault read/write access and no granular permission system [prior research background, S12-deepwiki excerpt from earlier research]. Auto-installing them is a real supply-chain trust decision on the user's machine — it must stay opt-in with an explicit, informative prompt (naming exactly what's being installed and from where), never silently defaulted to `true` the way a stored `unset` currently behaves for some existing MCP keys.
- Everything written by this automation (`.obsidian/plugins/`, `.obsidian/community-plugins.json`, the Obsidian app itself) is machine-local and gitignored already — consistent with the existing MCP-registration model. Nothing here should try to make plugin configuration shared/committed; that would be a materially different, bigger decision (vendoring three plugins' compiled JS into git history) that this research does not recommend.
- The vault root matters: opening the whole project root (not just `wiki/`) as the Obsidian vault is the natural choice, since `wiki/` pages already link back into `raw/` with relative paths (`../../../raw/...`) that only resolve correctly if both directories are inside the same vault.
- `run_project_sync()` must stay non-fatal end-to-end — a new Obsidian step must follow the same `if ! step; then warn; continue; fi` discipline already used for the MCP-install call, so a failed `brew install` or a GitHub API rate-limit on plugin downloads never blocks the rest of `setup`/`update`.
- GitHub's unauthenticated REST API is rate-limited (60 req/hr per IP) — fetching three plugins' `releases/latest` plus their asset files is well within that on a single run, but repeated `update` runs across many projects on the same network could matter; the installer should treat a rate-limit response the same as any other soft failure (warn, skip, continue) rather than erroring out.

## Solution Comparison

| Criteria | Do nothing (status quo) | App-only automation | Plugins-only automation | Both (recommended) |
|---|---|---|---|---|
| **Approach** | User manually installs Obsidian + plugins if they want them | Setup script installs the Obsidian app via brew/winget/flatpak; plugins stay manual | Setup script pre-stages plugin files in `.obsidian/plugins/` + enables them; app install stays manual | Setup script does both, each independently opt-in |
| **Pros** | Zero risk, zero new code | Removes the biggest manual step (downloading/installing a GUI app) | Plugins are ready the instant the user opens the vault in any Obsidian they already have; no GUI-app dependency in the installer at all | Fresh machine → open Obsidian once → vault, app, and all three plugins are already working |
| **Cons** | User has to learn and do all of this by hand, and the prior research's whole payoff (querying/visualizing typed links) stays unrealized indefinitely | Plugins still need manual GUI setup — most of the actual value (typed-link querying/visualization) is undelivered | If the user has no Obsidian installed yet, pre-staged plugin files just sit there until they install the app themselves (harmless, but less immediately gratifying) | Two separate consent prompts to design/maintain instead of one |
| **Complexity** | None | Low | Medium (GitHub Releases API calls, manifest-id-driven directory naming, JSON merge) | Medium — same as plugins-only, app install is low-complexity on top |
| **Dependencies** | None | Native package manager per OS (already assumed present by other steps, e.g. `npm`) | `curl`/`node` (already dependencies of this toolchain) | Both |
| **Codebase fit** | Perfect, but leaves the prior research's recommendation unrealized | Partial — half the value | Partial — the more valuable half, but assumes the user installs/has Obsidian separately | High — matches the existing guarded/opt-in pattern for MCPs and guides exactly |
| **Maintenance** | Zero | Low — one command per OS, rarely changes | Low-medium — plugin IDs/repos are stable, but "latest release" fetches should be re-run on `update` to pick up plugin updates | Low-medium, same as plugins-only |

## Recommendation

**Implement both, as two independently-gated steps inside a new `lib/scripts/install-obsidian.sh`, called from `run_project_sync()` right after the wiki scaffold sync.**

**Implementation outline:**

1. **New script `lib/scripts/install-obsidian.sh [--interactive] [--project-dir <dir>]`**, following `install-mcps.sh`'s exact shape (source `lib.sh`, parse the same two flags).
2. **Step A — app install**, gated by a new sticky key `obsidian.installApp` (scope: `global` — the app is machine-wide, not per-project, matching `mcp.playwright`'s scope choice):
   - Skip if an Obsidian install is already detectable (`/Applications/Obsidian.app` on macOS, `command -v obsidian`/registry check on Windows, `flatpak list | grep md.obsidian.Obsidian` or `command -v obsidian` on Linux) — mirrors the `mcp_installed` short-circuit-first discipline in `register_optional_mcp`.
   - `prompt_yn_sticky obsidian.installApp --global "Install the Obsidian app (recommended local viewer for wiki/ — https://obsidian.md)? [Y/n]: "`.
   - Adder: `case "$(uname -s)" in Darwin) brew install --cask obsidian ;; Linux) flatpak install -y flathub md.obsidian.Obsidian ;; *) echo "  Obsidian: unsupported OS for auto-install — see https://obsidian.md/download" ;; esac` (Windows path via WSL bash would need a `winget.exe` shellout, or this step is simply skipped on Windows with a printed manual command — call this out explicitly rather than silently no-op).
3. **Step B — plugin install**, gated by a new sticky key `obsidian.plugins` (scope: `project` — plugin files live inside this project's `.obsidian/`, matching `guides.*`'s project scope):
   - `prompt_yn_sticky obsidian.plugins "$PROJECT_DIR" "Install recommended Obsidian plugins (Dataview, Graph Link Types, Breadcrumbs) into this project's vault config? [Y/n]: "`.
   - For each of the three plugins (repo slugs: `blacksmithgu/obsidian-dataview`, `natefrisch01/Graph-Link-Types`, and Breadcrumbs' current repo — confirm the maintained fork at install time, since prior research noted a maintainer handoff): `curl` the `releases/latest` API, fetch `manifest.json` first to read the authoritative `id`, then `main.js` + `styles.css` (if listed) into `$PROJECT_DIR/.obsidian/plugins/<id>/`, then merge `<id>` into `$PROJECT_DIR/.obsidian/community-plugins.json` via a small idempotent `node -e` snippet in the same style as `_disable_project_playwright_locally`.
   - Non-interactive mode (plain `install-global.sh`/CI path): same "only a stored `false` diverts" rule as `register_optional_mcp`'s non-interactive branch — never silently install on a headless run without a prior recorded consent.
4. **Add both keys to `lib/scripts/templates/bootstrap-prefs-schema.json`** with the same `scope`/`consumer`/`summary`/`detail`/`values`/`default`/`askedBy` shape as every existing entry.
5. **Wire the call into `run_project_sync()`** (`lib/scripts/lib.sh:149`) between the wiki-scaffold sync and the MCP-guide build, wrapped in the same `if ! "$script_dir/install-obsidian.sh" ...; then echo "Warning: ... continuing"; fi` non-fatal guard already used for `install-mcps.sh`.
6. **Do not touch `/task-audit` or add Dataview query blocks to any generated file as part of this work** — both are legitimate, separately-scoped follow-on tasks (see Key Findings #5), not implied by "install the plugins."

**Risks and mitigations:**
- Risk: a user declines the app install but accepts plugin pre-staging, and is confused why "nothing happened." Mitigation: the plugin-install success message should explicitly say "Ready — open this project's folder as a vault in Obsidian to use them," since the two steps are intentionally decoupled.
- Risk: GitHub API rate-limiting during plugin fetch. Mitigation: treat as a soft failure (warn + skip that plugin, continue with the others), exactly like the existing Docker/launchd guards.
- Risk: a plugin repository is later renamed, archived, or forked (Breadcrumbs' own docs already flag an ongoing maintainer transition). Mitigation: pin repo slugs in one place at the top of the script (like `BRAVE_MCP_PORT`-style constants in `install-mcps.sh`) so a rename is a one-line fix, and fail soft with a manual-install pointer if a fetch 404s.

**Alternative if constraints change:** if this repo later wants plugin configuration to be *shared* across a team rather than machine-local, that requires deliberately un-gitignoring specific `.obsidian/` paths — a materially bigger decision (vendoring third-party compiled JS into git, cross-machine path assumptions) that should go through its own `/decision-create`, not be folded into this setup automation.
