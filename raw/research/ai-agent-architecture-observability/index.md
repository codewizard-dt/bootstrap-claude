# Research: AI Application Architecture — Single vs. Multi-Agent, Orchestration Patterns, and Observability

> Start with the simplest architecture that passes evaluation — a single augmented LLM, or a code-defined workflow — and only add a multi-agent orchestrator when a task is genuinely breadth-first/parallelizable and the ~4-15x token-cost multiplier is worth it [S9][S11]. When you do build multi-agent, the pattern that has actually survived production in 2026 is hierarchical orchestrator + isolated subagents, not peer-to-peer "group chat" [S13]. For frameworks, prefer your model vendor's own SDK (Claude Agent SDK, OpenAI Agents SDK, Google ADK) unless you specifically need LangGraph's graph/checkpointing machinery or CrewAI's role-based prototyping speed [S15][S17]; AutoGen is maintenance-only in 2026 [S18]. For observability, instrument with the vendor-neutral OpenTelemetry GenAI semantic conventions (`gen_ai.*` spans/metrics, still in "Development" status) and pick a backend by team profile — Langfuse for open-source/self-hosted, LangSmith if you're committed to LangGraph, Arize Phoenix for eval-heavy RAG work [S19][S22]. This repository itself is Claude Code tooling, not a deployed LLM application — but it already implements the orchestrator-worker pattern in its own skills (`power-mode`, `now`) [S1][S2] with zero observability instrumentation, while the Claude Code CLI it's built on ships built-in OpenTelemetry export (nested subagent spans, tool-call timing, per-hook spans) that this repo doesn't use or document anywhere [S25][S26].

## Research Questions

- When should an AI application use a single agent vs. a multi-agent architecture, and what does that decision actually cost?
- What are the dominant multi-agent orchestration patterns in production (orchestrator-worker, supervisor, hierarchical, swarm/mesh, handoff), and which one actually holds up?
- Which frameworks/packages (LangGraph, CrewAI, AutoGen, OpenAI Agents SDK, Claude Agent SDK, Google ADK, Microsoft Agent Framework, Mastra, Vercel AI SDK) fit which use cases in 2026?
- What does "comprehensive observability" mean for agentic systems — routing decisions, tool-call timing, latency, token/cost — and what's the current standard + tooling landscape?
- What does this repository already do that overlaps with these patterns, and where's the gap?

## Current State (Codebase)

`bootstrap-claude` is a Claude Code project-setup template — it ships skills, hooks, and MCP wiring for *other* projects, and is not itself a deployed LLM application with its own API integration code. Its closest analogue to "AI application architecture" is how its own skills orchestrate Claude Code subagents:

- **Orchestrator-worker, already implemented.** `lib/skills/power-mode/SKILL.md` is a hierarchical orchestrator: it drives tasks/roadmaps through a `tackle → uat-generate → uat-auto` pipeline, mandates a minimum team size of 5 collision-safe parallel agents per wave, and requires every spawned agent to carry a fixed footer instruction (Serena-first, `/research` on uncertainty) — this is the orchestrator-worker pattern from the literature [S1], almost exactly mirroring Anthropic's own lead-agent/subagent research-system architecture [S9].
- **A lighter orchestrator.** `lib/skills/now/SKILL.md` plans then delegates to at most 3 concurrent subagents — same pattern, smaller team, used for less parallelizable work [S2].
- **A deterministic-pipeline primitive.** The `Workflow` tool (see the `workflow-authoring` skill) offers `pipeline()`/`parallel()`/`phase()` script primitives for scripted multi-agent fan-out, gated behind explicit user opt-in ("ultracode") rather than being triggered autonomously — this matches Anthropic's "workflows are systems where LLMs and tools are orchestrated through predefined code paths" definition, kept deliberately distinct from open-ended "agents" [S11].
- **No observability instrumentation exists in this repo today.** There is no tracing, no metrics export, no structured logging of tool-call timing, routing decisions, or subagent token usage. The only persistent record of what happened is `wiki/log.md`, a manually LLM-authored, append-only markdown log — a human-readable audit trail, not telemetry [S3]. The `serena-health-tracking` hook (`lib/hooks/`) does some liveness tracking for the Serena MCP process specifically, but nothing at the level of "which skill/subagent called which tool, how long it took, what it cost."
- **The substrate already has the missing piece, unused.** Claude Code — the tool this entire repo configures — ships built-in OpenTelemetry support: metrics, log/events, and (beta) distributed traces over OTLP, gated behind `CLAUDE_CODE_ENABLE_TELEMETRY` / `OTEL_*` env vars. When a skill spawns subagents (exactly what `power-mode`/`now`/`Workflow` do), the child spans nest under the parent as one trace, giving delegation-chain visibility, per-tool-call timing, and per-hook spans out of the box — with token/cost metrics attributable by model, effort, and skill [S25][S26][S27]. Nothing in this repo currently surfaces, documents, or wires this up, despite it being the single most directly-applicable "integrated comprehensive observability for agent routing / tool calling / timing / performance" answer available to a Claude Code tooling repo specifically.

## Key Findings

### 1. Single agent vs. multi-agent is a cost/complexity decision, not a maturity ladder

- Anthropic's own research team found a multi-agent system (Opus lead + Sonnet subagents) beat a single agent by 90.2% on their internal breadth-first research eval — but at roughly **15x the token cost of a single chat interaction** (agents alone run ~4x a chat) [S9][beri.net summary in S9]. Token usage alone explained 80% of performance variance on their benchmark.
- The inverse is equally well documented: "we've seen teams invest months building elaborate multi-agent architectures only to discover that improved prompting on a single agent achieved equivalent results" — Anthropic's own follow-up guidance on when *not* to go multi-agent [S10].
- Industry data backs this as a general pattern, not an Anthropic-specific one: 40% of multi-agent pilots fail within six months of production deployment, mostly because teams pick the wrong orchestration pattern for the problem rather than because multi-agent doesn't work at all [S6]. A 2026 production benchmark found single-agent architectures often *outperform* multi-agent ones on latency and compute efficiency for tasks that don't need genuine parallel exploration [S4].
- Rule of thumb converged on across multiple 2026 sources: multi-agent earns its cost specifically for **breadth-first, parallelizable** work (independent facets of a query, independent files/records) — not for tasks with a single linear reasoning chain, where it adds latency and failure surface for no benefit [S9][S6][S8].

### 2. Orchestrator-worker (hierarchical) is the pattern that survived production; peer/group-chat did not

- Across architecture-pattern surveys, the dominant production model is **centralized orchestration**: a single orchestrator/supervisor agent assigns tasks, enforces policy, and monitors execution, with workers kept stateless or locally-scoped [S5][S7]. This matches both this repo's `power-mode`/`now` design and Anthropic's research-system architecture [S1][S2][S9].
- A 2026 production retrospective is blunt about the alternative: "orchestrator + isolated subagents... is where the entire industry converged in 2026. Peer collaboration (GroupChat) failed in production" — citing a cascade-failure paper showing a single false premise can propagate to 100% of agents in hub-and-spoke topologies under certain conditions, and worse under peer/mesh topologies [S13].
- Other named patterns worth knowing, each with a narrower fit: **supervisor/router** (one agent classifies and routes to a specialist, no shared execution state) [S7]; **pipeline/sequential** (fixed-order stages, e.g. document processing) [S6]; **swarm/mesh** (flat peer negotiation — higher quality on some diverse-consensus tasks per the AgentVerse research, but the failure mode above makes it the riskiest in production) [S4][S13].
- **Anthropic's 8 prompt-engineering principles for orchestrators** (directly reusable for any lead-agent design, including this repo's power-mode footer-instruction pattern): give every subagent an explicit objective, output format, tool/source guidance, and task boundary; embed effort-scaling rules so a simple query doesn't spawn 50 subagents; have subagents return a distilled summary, not their full transcript, back to the lead (raw transcripts pollute the lead's context and burn tokens at the 15x rate); scale subagent count to query complexity [S9][S13].

### 3. Compounding error is the core engineering risk of any multi-step or multi-agent system

- The math is unforgiving and appears identically across several independent 2026 sources: at 85% per-step accuracy (considered good), a 10-step chain succeeds only 19.7% of the time (0.85^10); only ~24% of agent tasks complete successfully on first attempt in a cross-industry 2026 benchmark [S30].
- In multi-agent specifically, errors compound *differently*: a stale or wrong output from step 2 poisons the context every downstream agent reads, and summarization introduces its own lossy-compounding error on top of that [S14][S30]. The documented fix is architectural, not prompt-level: decompose into small atomic subtasks whose outputs are independently verifiable before they enter any downstream context (a DAG of checkable units, not a monolithic chain) [S14].
- Anthropic's own alignment research flags a subtler version of the same risk at the behavioral level: individually-benign quirks in each agent can compound into unwanted *global* outcomes across a multi-agent system — a caution specifically about not assuming per-agent safety composes into system-level safety [S12].

### 4. Framework choice in 2026 is converging on five production-relevant options, with AutoGen retired

- Multiple independent 2026 comparisons converge on the same shortlist: **LangGraph** (graph-based, strongest state/checkpointing/durability, steepest learning curve — the enterprise default when auditability matters), **CrewAI** (role-based, fastest prototype-to-demo, weaker production checkpointing), **OpenAI Agents SDK** (handoff-based, lowest friction if GPT-centric), **Google ADK** (hierarchical, GCP/Gemini-native, strong multimodal + A2A protocol support), and **Microsoft Agent Framework** (the GA'd 2026 merger of AutoGen + Semantic Kernel, the Azure/.NET-native choice) [S15][S17][S18].
- **AutoGen is explicitly maintenance-only as of 2026** — bug/security fixes only, no new features, superseded by Microsoft Agent Framework; multiple sources advise against starting new projects on it [S16][S18].
- **Vendor-native SDKs (Claude Agent SDK, OpenAI Agents SDK, Google ADK) are consistently recommended over the provider-neutral frameworks when you're already committed to one model provider** — they ship tool use, memory, and tracing without the abstraction tax of a framework, and staying aligned with your provider reduces integration friction at the cost of preserved optionality [S16][S15].
- For TypeScript specifically: **Vercel AI SDK** owns the "AI feature bolted onto an existing Next.js app" case (streaming, RSC, tool-calling UI); **Mastra** owns the "agent product is the whole backend" case (bundles agents, graph workflows, memory with automatic compression, evals, and observability/Studio into one framework); the common production composition is AI SDK for the UI/streaming layer with Mastra underneath for orchestration/state — not an either/or [S28][S29].
- Important caveat specific to this skill's own defaults: `claude-agent-sdk` / `@anthropic-ai/claude-agent-sdk` (option 4 in the Claude API skill's four-approaches table) is *not* the same package as the API's Tool Runner (`client.beta.messages.tool_runner`) — both are harness-only (you host/deploy either way), but the Agent SDK ships the full Claude Code harness with built-in filesystem/bash tools, while the Tool Runner only loops over tools you define yourself. Framework literature outside Anthropic's own docs blurs this distinction; get it from the primary source, not a survey article, before choosing between them.

### 5. Observability has a real emerging standard (OTel GenAI semconv) but it isn't stable yet, and the tooling splits into two layers

- The industry is converging on **OpenTelemetry's GenAI semantic conventions** (`gen_ai.*` attributes, `invoke_agent`/`execute_tool`/chat spans) as the vendor-neutral instrumentation layer for LLM calls, agent steps, and tool executions — most major agent frameworks (OpenAI Agents SDK, LangChain, LlamaIndex, AutoGen) shipped emitters for it by Q1 2026 [S19][S21][S20].
- **Caveat that matters for any adoption decision: as of mid-2026 the agent-specific spans are still marked "Development," not "Stable"** — the spec's own transition plan says it will be updated before conventions are marked stable, with no committed timeline. Building on it today is described as "a reasonable bet," not a finished standard — expect attribute churn [S20].
- Tooling splits into two layers that solve different problems, and most mature setups use both: **proxy tools** (Helicone, Portkey) capture cost/latency with zero instrumentation but can't see the agent orchestration graph; **SDK/OTel-based tracers** (Langfuse, Arize Phoenix, LangSmith, Weights & Biases Weave, Braintrust, Traceloop/OpenLLMetry) trace actual agent steps and tool spans [S23].
- Backend choice is a team-profile decision, not a universal ranking, and every comparison source agrees on the same shape: **Langfuse** for OSS/self-hosted/data-sovereignty needs (MIT license, strong prompt management and eval harness) [S22][S24]; **LangSmith** if the stack is LangChain/LangGraph (deepest integration, node-by-node state diffs, replay against new model versions) but highest vendor lock-in [S22]; **Arize Phoenix** for eval-heavy RAG/ML-adjacent teams (fully open-source, OTel-native) [S22][S24]; **Braintrust** for eval-first regression-gated CI/CD workflows (most generous free tier: 1M spans/month) [S24]. A benchmarked overhead comparison found LangSmith had the lowest measurable latency overhead of the platforms tested, with Langfuse/AgentOps showing 12-15% overhead in a multi-step agent workload due to more decoupled instrumentation paths [S22].
- **Directly relevant to this repo:** Claude Code itself already implements this stack natively for the harness this repo builds on. It exports metrics (token/cost by model/session/subagent), log events (`prompt.id`-correlated, tool-call and hook events), and beta distributed traces (nested subagent spans, `llm_request`/`tool.execution`/hook spans with OTel `ERROR` status on failure) over standard OTLP — pointed at any OTel Collector, which can then fan out to Prometheus/Grafana, Jaeger, or any of the commercial backends above [S25][S26][S27]. This is a zero-new-code observability win specific to Claude Code tooling repos that nothing in this repo currently surfaces.

## Recommendation

**For target projects using this template that build actual LLM-powered applications:**

1. Default to the simplest tier — single augmented LLM call, then a code-defined workflow, then a custom single agent — and only reach for multi-agent when the task is demonstrably breadth-first/parallelizable and you've measured that a single well-prompted agent can't do it [S9][S10][S11]. This mirrors the Claude API skill's own "Should I Build an Agent?" gate (complexity / value / viability / cost-of-error), which is the same discipline the wider industry converged on independently.
2. If multi-agent is justified, use the **orchestrator + isolated-subagents** pattern (not peer/group-chat) and apply Anthropic's 8 delegation principles verbatim: explicit objective/format/tools/boundaries per subagent, summary-not-transcript returns, effort-scaled subagent count [S9][S13].
3. Pick framework by provider commitment first: vendor-native SDK if single-provider, LangGraph only if you specifically need graph/checkpointing durability, CrewAI only for fast role-based prototyping, Mastra/Vercel AI SDK split for TypeScript stacks. Treat AutoGen as legacy.
4. Instrument with OTel GenAI semantic conventions from day one, accepting that the agent-span portion will still churn (Development status) — this buys backend portability (Langfuse ↔ Phoenix ↔ LangSmith ↔ a self-hosted Collector) instead of a bespoke schema per vendor [S19][S20].

**For this repository specifically:**

1. **Document and optionally wire up Claude Code's built-in OpenTelemetry export.** This is the single highest-leverage, lowest-cost finding from this research for a Claude Code tooling repo: `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus `OTEL_*` env vars already gives nested subagent-delegation traces, per-tool-call timing, per-hook spans, and token/cost metrics by model/skill/session — exactly the "agent routing, tool calling, timing, performance" observability asked for in this research prompt — with zero new code in this repo [S25][S26][S27]. Candidate concrete next step: a new optional `wiki/guides/observability.md` (tier-wise delivered like `evals-framework.md`) documenting setup, plus an opt-in step in `install-global.sh`/`bootstrap-prefs` analogous to the existing guarded-install pattern for MCPs.
2. The existing `power-mode`/`now`/`Workflow` orchestration vocabulary already matches the literature's best-supported pattern (hierarchical orchestrator-worker) — no architectural change indicated there, only the observability gap above.
3. If/when this repo (or a target project) needs a backend beyond raw OTLP-to-Collector, Langfuse is the best-supported self-hosted default given this repo's general preference for owned/portable tooling over vendor lock-in (matches the existing pattern seen in [[serena-mcp-scope]]-style decisions elsewhere in this wiki).

## Risks and Mitigations

- **Risk:** Adopting OTel GenAI semantic conventions today means re-touching instrumentation when the spec stabilizes. **Mitigation:** treat attribute names as provisional; keep a thin translation layer (or rely on a backend like MLflow/Uptrace that already auto-translates) rather than hand-rolling dashboards against exact attribute names [S20][S19].
- **Risk:** Over-adopting multi-agent orchestration where a single agent would do, inflating cost 4-15x for no quality gain [S9]. **Mitigation:** measure single-agent performance first; only escalate team size when a measured breadth-first bottleneck exists, matching this repo's own "collision-safe parallelization" gate in `power-mode`.
- **Risk:** Peer/group-chat multi-agent topologies are the documented production failure mode (hub-injection cascades, unresolved circular disagreement) [S13][S30]. **Mitigation:** this repo already avoids this — `power-mode`/`now` are strictly hierarchical orchestrator→worker, never peer-to-peer; preserve that invariant in any future orchestration skill.
- **Risk:** Enabling Claude Code telemetry organization-wide without governance could leak prompt/tool-argument content (`OTEL_LOG_USER_PROMPTS`/`OTEL_LOG_TOOL_DETAILS` are opt-in but easy to over-enable). **Mitigation:** default to structural-only telemetry (durations, model names, token counts — no content) as Claude Code does out of the box, and treat content-logging flags as a deliberate, reviewed decision [S26][S27].
