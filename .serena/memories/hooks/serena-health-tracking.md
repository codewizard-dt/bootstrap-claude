# Serena Health Tracking & Fail-Open Enforcement (v2.9.0)

## Contract
Serena is ASSUMED HEALTHY (zero happy-path overhead). When a Serena tool call fails, health is assessed per-project; the process is diagnosed but **never terminated** by this hook chain; if no live process is found, ALL Serena-first guards fail open (exit 0) for the rest of the session. A separate Gate 1 backstop (below) catches the case where warmup itself never succeeds. Recovery is automatic on the next successful Serena call.

**2026-07-07 fix** (see `raw/research/serena-mcp-disconnect/index.md`, `wiki/knowledge/sources/serena-mcp-disconnect.md`): the pre-fix version of this system had a live-reproduced bug — `classifySerenaFailure` defaulted any unrecognized error string to `'transport'`, and the transport branch `pkill`'d the Serena process whenever it found one still alive after a failure, on the false premise that "alive but erroring" meant "hung." A hook only fires because the MCP round-trip completed with a payload to classify, which is proof the server responded — the opposite of hung. This killed a live, healthy Serena process on ordinary benign errors (e.g. `get_symbols_overview` on a file type not enabled in `.serena/project.yml`). Fixed by: (1) flipping the unknown-error default to `'tool'`, (2) removing the restart/pkill path entirely — `isSerenaProcessAlive` is now diagnostic-only, (3) adding a lock + atomic write around the state file (it's written by two different hook scripts on the same path with no prior coordination — a race could leave `should_enforce: true` even after the process was confirmed dead), and (4) a Gate 1 consecutive-block backstop as defense in depth.

## State
Health lives inside the existing per-project state file `~/.claude/state/lsp-ready-<md5(cwd).slice(0,12)>` under a `health` key: `{ should_enforce, healthy, error_count, last_error, last_check, notified }`. Top level also carries `warmup_block_count` (Gate 1 backstop counter, resets on any success). Missing file/key ⇒ enforce. `serena-session-reset.js` wipes the file at SessionStart (health resets per session — correct, since MCP server lifecycle is per-session). Full schema documented in `lib/hooks/README.md` ("State file JSON schema").

## Key code (lib/hooks/, mirrored to ~/.claude/hooks/ by install-global.sh)
- `lib/serena.js`: `getStateFilePath/readStateFile/writeStateFile` (writeStateFile is now atomic — temp file + rename), `acquireLock/releaseLock/updateStateFile` (dependency-free advisory lock + locked read-modify-write cycle — the single write path both `serena-usage-tracker.js` and `serena-first-read-guard.js` use), `defaultFlag/defaultHealth` (shared schema defaults), `shouldEnforceSerena`, `classifySerenaFailure` ('tool' = not-found/no-results/benign-decline/unrecognized → keep enforcing; 'transport' = timeout/connection/broken-pipe/genuinely-empty → assess, diagnostic only), `isSerenaProcessAlive(projectDir)` (pgrep scoped to `serena start-mcp-server` + project path — **read-only diagnostic, never drives a kill**), `isOutsideProject`, `extractSymbolsFromPattern`/`isCodeSymbol(token, opts)` (unified symbol detection). `attemptSerenaRestart` (the pkill function) was **removed** in the 2026-07-07 fix.
- `serena-usage-tracker.js` is the SINGLE writer of `health.*`, registered under BOTH `PostToolUse` and `PostToolUseFailure` with matcher `mcp__serena__.*|mcp__plugin_[^_]+_serena__.*` (wired in ~/.claude/settings.json). Success → restores health + resets `warmup_block_count`. Failure → classify → (if transport) diagnostic probe only → fail-open write + ONE-TIME systemMessage. Each of `handleSuccess`/`handleFailure` does exactly one `updateStateFile` call (one lock cycle).
- All 7 guards call `shouldEnforceSerena(readStateFile(getStateFilePath()))` before any block decision. `serena-first-read-guard.js` also writes to the state file (warmup/nav/read counters) — it and `serena-usage-tracker.js` are both callers of `updateStateFile`, which is why the lock exists (the state file has two independent writers, not one).

## Project-root scoping (user rule, same release)
SERENA-FIRST never applies to paths outside the project root — `isOutsideProject` is wired into read/edit/write guards (file_path), Grep/Glob guards (path param), and serena-bash-grep-block.js (segment allowed when every path target escapes the project; `$VAR`-led unresolvable paths allowed for read-only exploration commands, still blocked for in-place edits).

## Gotchas
- There is NO documented way to reconnect a stdio MCP server mid-session — this is why the fix removed the restart/pkill attempt entirely rather than trying to make it safer: it had no realistic upside and a confirmed downside. Fail-open + success-based recovery (or the Gate 1 backstop) is the guaranteed path.
- A benign empty `{}` PostToolUse tool_response is a NO-OP (not transport) — this was already handled correctly pre-fix (`respErrorKind` returns `'empty'`, never reaches `handleFailure`) and still is.
- Tool-level failures never flip `should_enforce` in either direction; only transport failures (no live process found) disable it, and only genuine successes re-enable it.
- The state file is written by TWO hook scripts (`serena-usage-tracker.js` for `health.*`, `serena-first-read-guard.js` for `warmup_done`/`nav_count`/`read_files`) — any future change to either must go through `updateStateFile`, not a raw `writeStateFile`, or the lock/atomicity guarantees silently stop applying to that write.
- Upstream `claude-code-lsp-enforcement-kit` was deliberately NOT synced (deferred); it has diverged.
