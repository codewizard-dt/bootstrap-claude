# prompts/

Markdown prompt templates for setup steps that are too context-sensitive for a static file copy — each one gets read by a script in `lib/scripts/`, interpolated with real project values, and handed to the `claude` CLI (`claude --print`) so Claude does the actual detection/generation work in the target project.

| Prompt | Driven by | Purpose |
|--------|-----------|---------|
| `setup-deployment.md` | `lib/scripts/setup-deployment.sh` | Detects deployable services (Node/Python/Go/Rust) from manifest files, then creates or updates `.github/workflows/security.yml` (always overwritten — generic CodeQL + Gitleaks), `.github/workflows/build.yml` and `.gitleaks.toml` (create-once, confirm before overwrite), and `Makefile` Docker targets (merged with existing targets, never removed/reformatted). Refuses to guess service names/entrypoints it can't confidently identify — stops and asks instead. |
| `migrate-wiki.md` | `lib/scripts/migrate-project.sh` | Drives the semantic conversion from a legacy `.docs/`-layout project to the LLM Wiki structure, after `sync-wiki-scaffold.sh` has already created the empty scaffold. Runs headlessly with only Bash/Read/Edit/Write (explicitly told not to look for Serena MCP tools). Hard rules: `git mv` every file before editing it (preserves history), never touch `raw/` or template-owned files (`wiki/conventions.md`, `lifecycle.md`), never move a file once it lands at its new path, and never commit — leaves everything staged for the user to review. Contains the full old-path → new-path mapping table (`.docs/tasks/` → `wiki/work/tasks/TASK-NNN`, `.docs/adr/` → `wiki/work/decisions/DEC-NNNN`, etc.) and the per-family status-inference rules. |
| `setup-strict-typechecks.md` | `lib/scripts/setup-strict-typechecks.sh` | Scans the repo for every language with a type-checking/linting story, researches current strict-mode conventions per language (TypeScript `strict` + `typescript-eslint` strictTypeChecked, Python `mypy --strict`, Go `staticcheck`/`vet`, Rust `deny(warnings)`/Clippy, …) via Context7/Brave Search, installs the required toolchain packages, and wires the config files plus a `make typecheck` target. Accepts an optional language list from the script's CLI args to scope the run. |
| `setup-design-system.md` | *(none — not currently invoked by any script)* | A generic prompt for wiring an arbitrary design system into a frontend app: migrate tokens/assets into `<APP_SRC_PATH>/design-system/`, wire the CSS import into the app entry point, then convert each prototype reference component into a typed production component driven entirely by CSS custom properties. Takes `<DESIGN_SYSTEM_PATH>`, `<APP_SRC_PATH>`, `<APP_ROUTES_PATH>`, and `<SKILL_NAME>` placeholders. Kept for manual reuse (`claude < setup-design-system.md` with placeholders filled in) when onboarding a design system other than the one `lib/skills/frontend-taste` already automates (house-style, from `~/code/house-style`). |

## Conventions

- Each prompt is a plain markdown instruction document, not a template engine — the driving script does simple string interpolation (e.g. substituting `__PROJECT_DIR__`) or appends args as plain text (e.g. the language list in `setup-strict-typechecks.md`) before piping the result to `claude --print`.
- Prompts that touch `wiki/` content reiterate the CRITICAL wiki rules from the root `CLAUDE.md` (immutable `raw/`, never edit template-owned files, `git mv` before edit) because they run in a fresh `claude` invocation with no access to this repo's own `CLAUDE.md` context.
- If a setup step's logic is static (file copy, directory creation, sentinel-guarded insert), it belongs in `lib/scripts/` or `lib/scripts/templates/` directly — a prompt here is only warranted when the step requires inspecting arbitrary target-project state and making judgment calls.
